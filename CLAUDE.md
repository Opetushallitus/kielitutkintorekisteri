# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Kielitutkintorekisteri (kitu) — OPH's register for language-exam data. Virkailija-facing Spring Boot app that also forwards records to the KOSKI service so they can be shown to citizens in Oma Opintopolku. Primary documentation and external API descriptions are linked from `README.md`.

## Toolchain

Tool versions live in `.mise.toml` and are installed automatically by `scripts/start_local_env.sh`: Java (corretto), Node, Maven, ktlint, prettier, shellcheck, aws-cli, go, `cdk-notifier` (PR diff comments in `_deploy-env.yml`), humanlog. **Kotlin and the Java release are _not_ in `.mise.toml`** — they live in `server/pom.xml` as `kotlin.version`/`java.version`. Read exact versions from those two files rather than restating them here; Renovate bumps them continuously. `AWS_PROFILE=oph-ktr-dev` and `SPRING_PROFILES_ACTIVE=local` are set by mise.

## Common commands

```shell
# One-shot dev env setup (installs mise deps, Playwright browsers, starts tmux with db+server).
# Pulls secrets from AWS Secrets Manager via the oph-ktr-dev profile.
./scripts/start_local_env.sh
./scripts/start_local_env.sh --setup-only   # skip tmux/containers

# Run the server standalone after the DB is up (wraps mvnw spring-boot:run + humanlog).
./scripts/start_local_server.sh

# Just the DB, Jaeger and LocalStack (S3)
docker compose up -d

# Backend build/test (in server/)
./mvnw package               # full build with tests
./mvnw test                  # tests only
./mvnw test -Dtest=OidTest   # single test class
./mvnw test -Dtest=OidTest#methodName

# Formatting (ktlint + prettier + shellcheck). CI runs the same script.
./scripts/check-formatting.sh
./scripts/format.sh          # auto-fix

# E2E Playwright (in e2e/)
npx playwright test
npx playwright test --ui
TEST_WORKERS=4 npx playwright test   # default 1, no cap in config; each worker boots its own server on 8080+index (CI forces 1)

# Infra (in infra/)
npm run diff/dev     # these pin TAG to `git rev-parse main` and pass --exclusively
npm run deploy/dev
TAG=$(git rev-parse main) npx cdk deploy --exclusively 'Dev/**'   # equivalent to the above
```

Backend tests spin up PostgreSQL via Testcontainers — Docker must be running. The Playwright suite expects the app's Maven build to launch it; see `e2e/README.md` for how to attach to an already-running IDEA debug session (`reuseExistingServer: true`).

**After switching branches, run `./mvnw clean` first.** Flyway reads migrations from the classpath (`target/classes/db/migration`), and neither Maven nor the Kotlin compiler deletes class/resource files whose source has disappeared — so a migration belonging to another branch keeps running against every fresh Testcontainers database. The symptom is a `column "…" does not exist` failure in tests the source tree says should pass.

## Architecture

### Layout

- `server/` — Spring Boot 4 + Kotlin backend. Source roots are `src/main/kotlin` and `src/test/kotlin` (configured in `pom.xml`, not the Maven defaults). Packages under `fi.oph.kitu/` are organized by **feature domain**, not by layer.
- `infra/` — AWS CDK (TypeScript) app. `bin/infra.ts` wires four stages: `Util` (shared ECR repo via `container-repository-stack`, GitHub Actions roles, plus its own `alarms-stack` for ECR vulnerability notices), then `Dev`/`Test`/`Prod`. Each env stage composes stacks (`service-stack`, `db-stack`, `network-stack`, `connections-stack`, `alarms-stack`, `log-groups-stack`, `backups-stack`, `route53-health-checks-stack`, `koski-audit-logs-integration-stack`, `github-actions-stack`, `dns-stack`). There are **no Prod-only stacks**: `yki-historia-upload-stack` was removed once the YKI-historia migration had been run, as were `bastion-stack` and `ecs-rds-proxy-stack` in `253dc088` — don't go looking for any of them. `infra/README.md` documents all 12 stacks. Deploys pick the container by `TAG` env var.
- `e2e/` — Playwright tests against a real server + Postgres.
- `scripts/` — bash helpers for local env, AWS profile/secret setup, tmux orchestration.
- `docs/` — published to GitHub Pages. `docs/technical/` is hand-written prose (arkkitehtuuri, koodikonventiot, integraatiot, yllapito) rendered by Jekyll — `build.yml` hard-checks those pages exist. The rest is generated: DB schema diagrams via SchemaSpy (`docs/build.sh`), component UML per environment (`docs/build-uml.sh`), db-scheduler docs.

### Feature domains (server packages)

Each domain typically contains its own `*ApiController`, `*ViewController` (server-rendered HTML via `kotlinx.html`), `*Service`, `*Repository`, entities, and `*ScheduledTasks`:

- `vkt/` — Valtionhallinnon kielitutkinnot
- `yki/` — Yleiset kielitutkinnot (suoritukset + arvioijat). Records arrive from Solki as **JSON pushes** (`POST /yki/api/suoritus`, `POST /yki/api/arvioija`). The old Solki **CSV import pipeline was removed** (commits `279bd81f`, `d160c1f1`, `ff82bc5a`) — don't go looking for a parser: `csvparsing/` is now **export-only**. **Versiointi / muuttumattoman datan tunnistus:** every push appends a row to `yki_suoritus` (`unique_suoritus` = `(solki_id, last_modified)`, and `last_modified` is `Instant.now()` at ingest, so ON CONFLICT never dedupes). The only guard is `YkiSuoritusRepository.save`, which compares the incoming entity against `findLatestBySolkiIds(...)` via `equalsIgnoringAnnotated(..., "DB")` and skips the write when they match. **Any entity field kitu writes itself — and that Solki therefore never sends — must carry `@IgnoreForEquality("DB")`**, or it diverges after the first write and every later push appends a no-change version (this was the cause of the duplicate history rows in prod: `koskiOpiskeluoikeus`, `koskiSiirtoKasitelty`, `arviointitilaLahetetty`, `arviointitilanLahetysvirhe`, `tarkistusarviointiHyvaksyttyPvm`). **The trap:** ignoring a field also makes kitu's _own_ write of that field a no-op, so such call sites must pass `forceWrite = true` — see `KoskiService`. Two further normalizations run before the comparison so that what we compare is what actually round-trips: `withTallennettavaTarkistusarviointi` (a tarkistusarviointi is reachable only through `yki_osakoe_tarkistusarviointi`, so one with no linked osakoe is unstorable and gets dropped; empty `arvosanaMuuttui` reads back as SQL NULL) and `withHyvaksyttyTarkistusarviointi` (`TARKISTUSARVIOINTI_HYVAKSYTTY` is kitu's own tila, so an incoming `TARKISTUSARVIOITU` is promoted to it before comparing — otherwise a re-push would silently revert the virkailija's hyväksyntä).
- **YKI-arvioijarekisteri — tila lasketaan, ei talleteta:** `yki_arviointioikeus.tila` on **vanhentunut** (V121: nullable, ei defaultia). Kitu kirjoittaa aina NULLin ja tila lasketaan kauden päivistä `Rekisterointitila.laske`ssa (PASSIVOITU jos päättymispäivä < tänään, TULEVAISUUDESSA jos alkupäivä > tänään, muuten AKTIIVINEN; päättymispäivä on inklusiivinen). **Vain tallennettu `PASSIVOITU` ohittaa laskennan** — tallennettu `AKTIIVINEN` sivuutetaan, koska V117 täytti sarakkeen sillä eikä se kanna tietoa. Ainoa ei-tyhjän arvon kirjoittaja on Solkin push (`Tallennuslahde.SOLKI`). Sama sääntö on kirjoitettu kahdesti — Kotliniksi ja `Rekisterointitila.SQL`:ksi listanäkymän suodatusta ja lajittelua varten — ja `YkiArvioijaTilaSqlTest` on ainoa asia joka pitää ne yhtenevinä. Listakysely **kääritään alikyselyyn** (`SELECT * FROM (...) arvioijarivi`): ilman sitä `ORDER BY tila` kaatuu (`ORDER BY "tila" is ambiguous`) ja WHERE osuisi hiljaa vanhentuneeseen sarakkeeseen, koska aliakset eivät näy WHERE-lauseessa. Päivä sidotaan parametrina (`:tanaan`) `TimeService`ltä, **ei** `CURRENT_DATE`:na — muuten kiinnitetty testikello ei ohjaa SQL:ää. Seuraukset: passivointi **päättää kauden** tähän päivään (ja vain kiristäen — muuten klikkaus pidentäisi vanhentunutta oikeutta), joten merkintä lukee "Aktiivinen" passivointipäivän loppuun; passivointinappi näkyy ehdolla `passivoitu == null`, koska säilytysajan alkuhetki on saatava asetettua myös luonnollisesti päättyneelle merkinnälle; ja `jatkorekisterointi` johdetaan (`kaudenAlkupaiva > ensimmainenRekisterointipaiva`) eikä tule enää lomakkeelta.
- **YKI-arvioijarekisteri — arviointikausi on master, `yki_arviointioikeus` projektio:** kausi on **arvioijakohtainen**, ei kielikohtainen (OPH: _"henkilöllä ei ole päällekkäisiä arviointikausia vaan kaikilla sama kausi"_), ja elää V122:n `yki_arvioija_arviointikausi` + `..._oikeus` -tauluissa, joilla on pysyvä id. Virkailija lisää, muokkaa, passivoi ja poistaa kausia tietosivulta (`/yki/arvioijat/{id}/kaudet/**`). `yki_arviointioikeus` on **johdettu**: `Kausiprojektio` valitsee projisoitavan kauden (voimassa oleva > tuleva > viimeisin päättynyt) ja `YkiArvioijaKausiRepository.paivitaProjektio` kirjoittaa sen — **vain jos jokin arvo tosiasiassa muuttui**, muutoin yöllinen ajo leimaisi koko rekisterin muokatuksi ja lähettäisi sen uudelleen Solkiin. Näin `Rekisterointitila.SQL`, listanäkymä ja Solki-lähetys jatkavat ennallaan. Kolme ansaa: (1) valinta riippuu kuluvasta päivästä, joten projektio vanhenee kun tuleva kausi alkaa — sen korjaa `kitu.yki.scheduling.paivitaArvioijaProjektiot`, joka on **kytketty `integraatioKaytossa`-lippuun** — täysi sisääntuleva push kirjoittaa projektion koskematta kausimasteriin, joten taulut ovat taatusti eri linjoilla ja koko rekisterin yliajo vanhentuneesta masterista työntäisi sen lisäksi Solki-lähetysjonoon; (2) **säilytysaika ei saa lukea pelkkää projektiota** — `Sailytysaika.ALKUHETKI_SQL` ottaa `GREATEST`in projektiosta ja masterista ja `poistaSailytysajanYlittaneet` tarkistaa erikseen, ettei masterissa ole voimassa olevaa kautta, koska muuten vanhentunut projektio poistaisi yhä voimassa olevan merkinnän; (3) **arvioijatason passivointi katkaisee kaudet ennen `tallenna`a**, koska `tallenna` synkronoi kaudet oikeuksista — väärässä järjestyksessä syntyy uniikkiehdon rikkova duplikaattikausi. **Hallintopäätöksen ASHA-numero kuuluu kaudelle**, ei arvioijalle (V124): jokainen kausi on oma hallintopäätöksensä, joten arvioijatasolla jatkokausi olisi ylikirjoittanut edellisen viitteen. Numero kulkee myös projektioon, jotta listanäkymän haku, lajittelu ja CSV jatkavat ennallaan. Vanhentuneet kielet (`SWE10`, `ENG11`, `ENG12`) **eivät kuulu kausiin** lainkaan: ne jäävät jäädytetyiksi `yki_arviointioikeus`-riveiksi ja näkyvät tietosivulla omassa vain-luku-osiossaan. `yki_arvioija_kausi` säilyttää nimensä mutta on nyt pelkkä **muutosloki** (`toimenpide`-sarake, ei uniikkiehtoa) — uudelleennimeäminen rikkoisi rinnakkain ajossa olevan vanhan sovellusversion tietosivun. §2.4:n "kaikilla kielillä sama kausi" ja "uusi kieli perii voimassa olevan kauden" eivät ole validointisääntöjä vaan **rakenteellisia**: kaudella on yksi päiväpari ja N kielriviä.
- **YKI-arvioijarekisteri — integraatiokytkin ei koske käsin lähetystä:** `kitu.yki.arvioijarekisteri.integraatio.enabled` estää **automaattisen** lähetyksen Solkiin (tallennuksen jälkeinen synkroninen yritys, `lahetaLahettamattomat`, `SolkiArvioijaScheduledTasks` ja `paivitaArvioijaProjektiot`), mutta **ei** virkailijan tietosivulta painamaa "Lähetä uudelleen Solkiin" -painiketta: se kutsuu `SolkiArvioijaService.lahetaArvioijaKasin`ia, joka ohittaa kytkimen — yksittäinen lähetys on se tapa, jolla integraatiota kokeillaan ennen automaattisen liikenteen avaamista. Siksi `SolkiArvioijaClientImpl` ja `SolkiArvioijaServiceImpl` ovat **ehdottomia beaneja**; aiempi `@ConditionalOnProperty` + `SolkiArvioijaServiceMock` -pari poisti koko lähetyskoneiston kytkimen ollessa pois, jolloin painiketta ei voinut toteuttaa. Painike on silti **muokkauskytkimen** takana, koska POST-reitti on. Onnistunut käsin lähetys poistaa rivin lähetysjonosta ja epäonnistunut kirjaa `solki_lahetysvirhe`n normaalisti.
- **YKI-arvioijahakemukset atarusta (`ataru/` + `yki/arvioijat/hakemus/`):** eräajo hakee atarun arvioijahakemuslomakkeen hakemukset ja kutsuu niille `YkiArvioijaService.luoArvioija`a (`tekija = null`), joka ylikirjoittaa olemassa olevan arvioijan yhteystiedot ja lisää jatkokauden; kausi alkaa tänään tai voimassa olevan/tulevan kauden päättymistä seuraavana päivänä. Lomakkeen avain ja kenttä-id:t (`ArvioijahakemusLomake`) sekä ehdot (`ArvioijahakemusKriteeri`) ovat **kovakoodattuja** — ainoat asetukset ovat `kitu.ataru.service.url` (tyhjä = koko integraatio pois, beaneja ei synny) ja `kitu.ataru.arvioijahakemus.schedule`. Tila elää taulussa `yki_arvioijahakemus` (V130): rivi = hakemus käsitelty eikä sitä haeta uudelleen — **paitsi `ODOTTAA_YKSILOINTIA`** (henkilöä ei ole vielä yksilöity tai luotu), joka haetaan joka ajolla uudelleen kunnes se ratkeaa. Ennen `luoArvioija`a rivi kirjataan tilaan `KASITTELYSSA` ja viimeistellään sen jälkeen, joten kaatuminen niiden välissä jättää rivin näkyviin eikä luo seuraavalla ajolla toista kautta; yksittäisen hakemuksen poikkeus ei pysäytä muita, vaan ajo heittää vasta lopuksi. Taulu on **pelkkä kirjanpito ilman säilytysaikaa** — älä lisää sille poistoa, sillä poistettu rivi saisi seuraavan ajon luomaan arvioijan uudelleen, joten **ohimenevät virheet (ONR ei vastaa, samanaikainen muokkaus) jätetään tarkoituksella kirjaamatta**. Ansat: (1) ataru hyväksyy **vain CAS:n**, ei OAuth2:ta — `security/cas/client/CasSessionClient` on kitun ainoa lähtevä CAS-asiakas (TGT → ST → `ring-session`-eväste, 401 → uudelleenkirjautuminen); (2) `koto-rekisteri` saa `ATARU_HAKEMUS` READ -oikeuden lomakkeen omistavaan OPH:n **alaorganisaatioon** (ei juureen, joka tekisi siitä ataru-superuserin), ja puuttuva oikeus näkyy **tyhjänä vastauksena, ei virheenä**; (3) listaus käyttää atarun virkailija-UI:n reittiä `/api/applications/list`, joka ei ole sovittu ulkoinen rajapinta; (4) lomakkeen vuoden raja kauden alkupäivälle (`validateKaudenAlkupaiva`) **ohitetaan** automaattiselle jatkokaudelle `TallennaArvioija.automaattinenJatkokausi`-lipulla, koska jatkokausi alkaa vasta voimassa olevan kauden päätyttyä — lippu ei ole vapaa ohitus, vaan `TallennaArvioijaValidation` vaatii silloin, että jokin olemassa oleva kausi päättyy alkupäivää edeltävänä päivänä. e2e/`local-opintopolku` käyttää `MockAtaruClient`ia (fixture `opintopolku-mocks/ataru/`).
- `kotoutumiskoulutus/` — integrates with the Koealusta kielitesti service. **Valmiit ovat inkrementaalisia, keskeneräiset täysi korvaus:** `importValmiitSuoritukset` saa `from`-vesileiman db-schedulerilta (`recurringStatefulTask<Instant>`) ja tallentaa vain uudet, kun taas `importKeskeneraisetSuoritukset` tekee joka ajolla `deleteAllKeskeneraiset()` + `saveAll`. Keskeneräisten haku rajataan Moodlen `enrolledfrom`-parametrilla (`timeService.now()` miinus `kitu.kotoutumiskoulutus.koealusta.keskeneraiset.enrolmentWindow`, oletus `14d`, `kotlin.time.Duration`; **tyhjä arvo jättää parametrin pois**, mikä on se tapa perua rajaus jos Mediamaisterin pää ei vielä tunne parametria). **Siksi ikkuna on samalla säilytysaika**: ikkunasta valunut keskeneräinen katoaa seuraavassa ajossa, eikä tälle ole saraketta tai migraatiota. **Kaikki Moodle-aikaleimat ovat epoch-sekunteja** molempiin suuntiin (`.epochSecond` / `Instant.ofEpochSecond`) — laske ikkuna `timeService.now()`:sta, älä `today()`:stä, muuten palaa Europe/Helsinki-vs-UTC-ansa. Keskeneräisten kartoitus nojaa siihen, että `KoealustaMappingService` on tarkistanut `isOnrValidateable()`-ehdon ennen `courseToEntity`-kutsua; validaattori ei tarkista `preferredname`a enää uudelleen, eikä `courseToEntity` siksi enää palauta nullia. Molemmat koealusta-ajot jakavat yhden `...koealusta.scheduling.import.schedule`-arvon. **Testiansa:** `KoealustaServiceTests` jakaa yhden kontekstin ja yhden `MockRestServiceServer`in kaikkien testiensä kesken (`PER_CLASS` + `reset()` `@BeforeEach`issä). Inline-`properties` antaa luokalle oman kontekstiavaimen, joten `KoealustaService`n laiska `RestClient` ei ole ehtinyt rakentua ennen sidontaa, ja `AFTER_CLASS` sulkee kontekstin ettei mock vuoda muihin luokkiin. **Älä palauta `BEFORE_EACH_TEST_METHOD`ia**: se rakensi kontekstin 24 kertaa ja vei ~6 min CI:n ~8 min testiajasta. Samasta syystä testit eivät saa olettaa id-sekvenssin alkavan ykkösestä, ja testin muuttamat palvelun kentät (`keskeneraisetEnrolmentWindow`) palautetaan `@BeforeEach`issä.
- **YKI-historian karanteenitaulu** `yki_historia_siirtymaton` (V127): YKI-historiamigraatiossa (2011–2016) siirtymättä jääneet lähderivit sellaisenaan + syy. **Taululla ei ole enää lainkaan sovelluskoodia**: listanäkymä `/yki/historia-siirtymattomat`, sen CSV, etusivun laskuri ja dev-mockdata-reitti poistettiin — taulu säilytetään kannassa, dataa luetaan tarvittaessa SQL:llä. Rivit ladattiin kerran CloudShellista **RDS Data API:n** kautta migraatioskriptillä, joka on sittemmin poistettu, eikä taululle ole enää latausreittiä. **V129 siirtää muunnettavissa olevat rivit rekisteriin** (`yki_suoritus` + `yki_osakoe` + tarkistusarviointi) ja **poistaa ne karanteenista**; jäljelle jäävät ovat ne joita ei voi muuntaa, ja niiden `syy`/`syyluokka` kirjoitetaan uudelleen, koska `EI_OPPIJANUMEROA` ei ole siirron jälkeen enää syy jäädä karanteeniin. Karanteenissa olevasta rivistä ei edelleenkään lähde mitään KOSKEen, ONR:ään tai ilmoittautumisjärjestelmään, eikä sitä lasketa suoritukseksi. **Kaikki lähdesarakkeet ovat TEXT ja talletetaan sellaisenaan**, koska juuri näissä riveissä ovat ne arvot joita ei voitu jäsentää (katkaistut hetut, jäsentymättömät aikaleimat, väärät sarakemäärät) — tyypitys hylkäisi juuri sen datan joka on tarkoitus saada talteen. Migraation skriptit ja runbook (`scripts/migrate_yki_historia.py`, `scripts/load_yki_historia_siirtymattomat.py`, `scripts/yki-historia-migration.md`) **on poistettu** ajon jälkeen; git-historia kertoo mitä ne tekivät.
- **YKI-suoritus ilman oppijanumeroa — sallittu kannassa, estetty kaikkialla muualla:** `yki_suoritus.suorittajan_oid` on **nullable V128:sta alkaen** ja `YkiSuoritusEntity.suorittajanOID` on `Oid?`. NULL on **vain 2011–2016 historiadatan erikoistapaus** (V129:n siirtämät rivit, joille oppijanumeroa ei saatu ONR:stä millään keinolla). Kolme asiaa pitävät sen erikoistapauksena: (1) **rajapinta ei päästä sellaista läpi** — `tiedontuontischema/Henkilo.oid` on ei-nullable ilman default-arvoa, joten Jackson kaatuu ja `GlobalControllerExceptionHandler` tekee siitä 400:n; erillistä validaattoria **ei ole eikä pidä lisätä**, ja `Henkilo` on yhteinen VKT:n kanssa joten kentän nullableksi tekeminen levittäisi muutoksen sinne turhaan (`YkiApiControllerTest` kiinnittää 400:n). (2) **KOSKI-siirto on estetty kahdessa kerroksessa**: `KoskiYkiRequestMapper.koskiSiirronEstonSyyt` lisää syyn "Suorituksella ei ole oppijanumeroa" (tämä on arvovaltainen portti ja näkyy tietosivulla sekä `/yki/koski-request/{id}`-reitillä), **ja** `findKoskeenLahettamattomatSuoritukset` suodattaa `suorittajan_oid IS NOT NULL`. Pelkkä mapperin esto ei riitä, koska `KoskiService` kirjoittaa `EstoSyyt`-haarassa `koskiSiirtoKasitelty = true` — rivi leimautuisi käsitellyksi eikä siirtyisi koskaan, vaikka oppijanumero myöhemmin saataisiin. (3) **Ilmoittautumisjärjestelmä samoin**: `YkiSuorituksenTunniste.of` palauttaa **nullin** ilman oppijanumeroa (ja `YkiArvioinninTila.of` sen myötä, samaan tapaan kuin `isVilppi()`-riveillä), ja `findSuorituksetWithUnsentArvioinninTila` suodattaa samalla ehdolla — ilman SQL-suodatinta rivi luettaisiin joka ajolla uudelleen, koska nulliksi mäppäytyvää ei koskaan merkitä lähetetyksi. Tietosivu **ohittaa ONR-haun** kun oppijanumeroa ei ole (`YkiViewController` kutsuu `getHenkiloByHenkiloOid`ia vain `?.let`-haarassa, ja `YkiSuoritusPage.render`in `henkilo` on nullable = "ONR:ää ei kysytty"), eikä tarjoa yksilöintilinkkiä joka johtaisi 404:ään.
- **SQL-migraatio joka kaytaa jasentymatonta dataa: `pg_input_is_valid`, ei casteja.** Flyway ajaa migraation yhdessä transaktiossa, joten **yksikin kaatuva cast kaataa koko migraation** — eikä `to_date` pelasta: `to_date('2011-02-30','YYYY-MM-DD')` kaatuu (se **ei** rullaa yli), kuten myös `make_date`, eikä `CAST(x AS date DEFAULT NULL ON ERROR)` ole tuettu. `pg_input_is_valid(teksti, tyyppi)` on totaali ja tuntee myös **domainit ja enumit**, joten esim. `iso_oid`-domainin regexp-CHECKiä ei tarvitse kirjoittaa uudelleen. **Vaatii Postgres 16+** (tuotanto on Aurora PostgreSQL 16.4, `infra/lib/db-stack.ts`). **Ansa:** `pg_input_is_valid(NULL, …)` on **NULL** eikä NULL ole tosi, joten paljas kutsu WHERE-lauseessa pudottaa hiljaa NULL-rivit — pakolliselle kentälle `col IS NOT NULL AND pg_input_is_valid(...)`, valinnaiselle `col IS NULL OR pg_input_is_valid(...)`. Enum-tarkistus on kirjainkoon suhteen tarkka (`fin` ei kelpaa, `FIN` kelpaa). Älä myöskään nojaa `AND`:in oikosulkuun castin suojana — Postgres ei takaa evaluointijärjestystä, joten käytä `CASE`ia tai `MATERIALIZED`-aitaa. Kuivaharjoittele predikaatti read-only-SELECTinä ennen ajoa. **Väliaikaistaulut: älä käytä `ON COMMIT DROP`**, vaan `DROP TABLE IF EXISTS` ennen luontia ja lopussa. Flyway ajaa migraation yhdessä transaktiossa, mutta `psql -f` ajaa **jokaisen lauseen omana transaktionaan**, jolloin `ON COMMIT DROP` tuhoaa taulun heti ensimmäisen lauseen jälkeen ja seuraava lause kaatuu `relation ... does not exist` -virheeseen — eli migraatiota ei voisi kuivaharjoitella eikä ajaa käsin lainkaan, mikä on juuri se mitä tuotannon datamigraatiolle halutaan tehdä. Huom myös ettei tämä näy Testcontainers-testissä, jos testi antaa koko tiedoston yhtenä `jdbc.execute`-kutsuna (Postgres ajaa monilauseisen kyselyn yhtenä implisiittisenä transaktiona).

### Cross-cutting pieces worth knowing

- **DB & migrations**: Spring JDBC (no JPA entity manager) over Flyway. Migrations in `server/src/main/resources/db/migration` (`V*__*.sql`). Schema docs are generated by `docs/build.sh` via SchemaSpy. The V-numbering has gaps (V7, V38, V46–V55, V65, V104, V105) left over from earlier mistakes — V65 was renamed to V67 to repair an out-of-order deploy (commit `04b1d07d`), and V104/V105 were renumbered to V108/V109 by the same kind of repair (`3b2c24bd`, `021153cd`). Highest in `main` is **V131**. Don't reuse skipped numbers; just continue past the highest.
- **Aika ja "tämä päivä" testeissä**: sovelluksen käsitys tästä päivästä on **aina `Europe/Helsinki`** — `TimeService.zoneId` kovakoodaa sen ja `TimeService.today()` johtaa päivän siitä. CI-ajurit ovat **UTC**:ssa, joten testi joka laskee oman "tämän päivänsä" `LocalDate.now()`:lla (JVM:n oletusvyöhyke) tai JS:n `new Date()`:lla on eri päivässä kuin palvelin klo **21–24 UTC** välillä, ja jokainen päivärajaan nojaava väite kääntyy. Oire: yöaikaan kaatuva testi, joka menee aamulla uusinta-ajolla läpi — näyttää "flakyltä" vaikka on täysin deterministinen. **Server-testit:** injektoi `TestTimeService` (profiili `test`) ja kiinnitä hetki `runWithFixedClock(...)`:lla, ja johda odotetut päivät `timeService.today()`:stä — älä käytä `LocalDate.now()`:ta. **E2E:** `playwright.config.ts` asettaa `process.env.TZ = "Europe/Helsinki"` (ja selaimen `timezoneId`) koko ajolle, jotta spekin `new Date()` vastaa palvelinta — älä poista sitä. Huom: kaikki testin `LocalDate.now()` ei ole vika — se on vika vain jos arvoa verrataan palvelimen laskemaan päivään (esim. `Rekisterointitila.laske` oikosulkee tallennettuun `PASSIVOITU`-tilaan, jolloin päiväargumentti on merkityksetön).
- **Scheduled work**: uses `db-scheduler` (kagkarlsson). Tasks are enabled/disabled per Spring profile via properties (`kitu.yki.scheduling.*`, `kitu.vkt.scheduling.*`, etc.). There's a db-scheduler UI mounted by the app; see `docs/db-scheduler/README.md`. The `db-scheduler-log` add-on is **vendored** at `server/src/main/kotlin/io/rocketbase/extension/` (port of 0.7.0 with SB4 package relocations) until an upstream SB4-compatible release exists — see the package README for the rollback procedure. Schedule strings go through `ExtendedSchedules.parse` (`util/scheduling/`): it accepts the built-in forms (`FIXED_DELAY|Ns`, `DAILY|HH:mm`, `-`) and falls back to **SPRID53 cron** (6 fields `sec min hour dom month dow`, `?` allowed, **no year field** — Quartz-style 7-field crons fail). **Gotcha for "manual"/on-demand tasks:** a `-` (disabled) schedule does **not** make a task that's triggerable from the UI — db-scheduler deliberately never creates a `scheduled_tasks` row for a disabled recurring task (and removes any existing one) in `ScheduleRecurringOnStartup`, and the UI lists only existing executions, so the task is invisible with no "Run now". To get a UI-triggerable-but-effectively-never-auto-running task, give it a rare real cron (e.g. `0 0 0 29 2 ?` = leap-year Feb 29) rather than `-`.
- **JSON**: Jackson 3 (`tools.jackson.*` packages, e.g. `tools.jackson.databind.json.JsonMapper`). Annotations still come from `com.fasterxml.jackson.annotation` (kept for backward compat). `JavaTimeModule` no longer exists — register `java.time` serializers via `SimpleModule()`. `ObjectMapper.copy()` is gone — use `.rebuild()...build()`. Accessor renames on `JsonNode`/`JsonParser`: `textValue()` → `stringValue()`, `asText()` → `asString()`, `p.text` → `p.string`. Custom deserializers should extend `ValueDeserializer<Any>` for `@JsonDeserialize(using = ...)` compatibility.
- **Config & profiles**: `application.properties` is the base; per-env overrides in `application-{local,local-opintopolku,untuva,qa,prod,e2e}.properties`. `ConditionalOnNonEmptyProperty.kt` is a custom condition used to wire beans only when a config value is set.
- **Offline dev (`local-opintopolku`)**: started by `scripts/start_offline_dev.sh` (which sets `SPRING_PROFILES_ACTIVE=local,local-opintopolku` — the override profile must come last). It needs no AWS secrets and no Untuva: ONR, organisaatiopalvelu, koodisto and CAS are replaced by in-process mocks (`/dev/mocklogin`, `/dev/oauth/token`). `MockOppijanumeroService` (profiles `test | e2e | local-opintopolku`) resolves henkilös from the fixtures in `resources/opintopolku-mocks/oppijanumerorekisteri-service/henkilo/*.json`, plus any `MockHenkilolahde` bean that contributes henkilös at runtime — fixtures win on an OID collision. The only such bean is `dev/YkiArvioijaMockHenkilolahde` (`local-opintopolku` only, so tests and e2e are unaffected): an `ApplicationRunner` that reads every `yki_arvioija` row at startup and exposes it as a henkilö, so arvioijat that exist in the local DB resolve by OID **and** by hetu instead of 404ing out of the mock ONR. It is a startup snapshot — restart after inserting arvioijat outside the app.
- **Secrets**: never hard-coded. Local dev pulls from AWS Secrets Manager via `scripts/ensure_aws_secrets.sh` (`kielitesti-token`, `palvelukayttaja-password`, `palvelukayttaja-oauth-password`, `yki-api-user`, `yki-api-password`). The secrets that must exist manually per AWS account are the ones `infra/lib/service-stack.ts` injects: those same five plus `tolgee-api-key` on the Test account (QA) only. **There is no `oppijanumero-password`** — ONR auth runs off `palvelukayttaja-password` → `PALVELUKAYTTAJA_PASSWORD` → `kitu.palvelukayttaja.password`; the old name survived in the docs long after anything read it.
- **Auth / CAS single logout**: browser auth is CAS (Otuva) — `CasAuthenticationFilter` is wired in `security/cas/CasConfig.kt`, `SingleSignOutFilter` one package up in `security/WebSecurityConfig.kt`. Otuva does **back-channel** single logout: on `/cas/logout` (e.g. from the virkailija-raamit menu) CAS POSTs a `logoutRequest` to the service URL and the service must invalidate **its own** session — CAS never clears the browser `SESSION` cookie. Because kitu uses **Spring Session JDBC**, the apereo filter's default in-memory `SessionMappingStorage` can't find/invalidate the DB session (and breaks across instances), so it's wired via the **static** `SingleSignOutFilter.setSessionMappingStorage(...)` to a DB-backed `JdbcSessionMappingStorage` (service-ticket→Spring-Session-id in table `cas_client_session`; `session_id` is deliberately **not** UNIQUE — one browser session can hold several tickets, OPH KJHH-2045). Don't push injected deps into an abstract base (`@WithSpan` CGLIB trap) and don't add a session-fixation strategy to the manual `CasAuthenticationFilter` — it sets none, so it keeps `AbstractAuthenticationProcessingFilter`'s no-op default and the session id stays stable, which is what keeps the login-time ST→session mapping valid. Consequence: `CasUserDetails` attributes (incl. `asiointikieli`, see i18n) are a **login-time snapshot** and only refresh on a real re-login.

- **Modaalit ovat natiiveja, ilman JS:ää**: `html/Modal.kt` renderöi `<dialog>`in ja avaa/sulkee sen **Invoker Commands** -attribuuteilla (`commandfor` + `command="show-modal"|"close"`) — sivuilla ei ole lainkaan modaaliin liittyvää JavaScriptiä, joten kaikki nojaa selaimen natiiviin toteutukseen. **Ansa:** komentonapin **täytyy** olla `type="button"`, jos se on `<form>`in sisällä. Ilman sitä napin tyyppi jää Auto-tilaan, ja vaikka `button.type` palauttaa IDL-tasolla `"button"` eikä lomaketta lähetetä, Chromium ei aja komentoa lainkaan: `command`-tapahtumaa ei synny ja **klikkaus ei tee yhtään mitään** (näin kävi vahvistusdialogien Peruuta-napille, joka elää `formPost`in sisällä). Siksi `modalCommandButton` kirjoittaa `type = ButtonType.button` aina — älä poista sitä. Dialogin ulkopuolinen avausnappi toimi ilmankin vain siksi, ettei se kuulu mihinkään lomakkeeseen.
- **Ohje-painike ja wikilinkit käännöksinä**: `Page.renderHtml(ohje = UiText.Ohje.…)` piirtää yläpalkin oikeaan reunaan "Ohje"-linkin (`data-testid="ohje-linkki"`, uuteen välilehteen). URL:t ovat **käännösavaimia** (`ohje.*` `UiText.Ohje`ssa + `lokalisointi/fi.json`), jotta OPH:n virkailija voi vaihtaa ne Tolgeessa ilman deployta, ja kieliversion wikisivu on pelkkä sv/en-käännös. `html/Ohje.kt`:n `ohjeUrl` käyttää sivukohtaista arvoa vain jos se alkaa `http(s)://`; tyhjä, puuttuva (joka muuten renderöityisi raakana avaimena) tai virheellinen arvo palaa `ohje.oletus`een. Siksi sivukohtainen avain jolla ei ole omaa sivua on fi.json:ssa **tyhjä merkkijono** — ja `TolgeeClientImpl.createKeys` luo tyhjän lähdetekstin avaimen ilman fi-käännöstä. Uusi näkymä: lisää `ohje.<alue>.<sivu>`-avain molempiin ja välitä se `renderHtml`ille; ilman parametria sivu saa oletusohjeen.
- **Virhesivut HTML-näkymissä**: a virkailija view signals "ei löydy" by **throwing** a subclass of `webmvc/ResourceNotFoundException` — one per domain, declared at the bottom of the owning `*ViewController.kt` (`VktSuoritusNotFoundError`, `YkiSuoritusNotFoundError`, `YkiArvioijaNotFoundError`, `KielitestiSuoritusNotFoundError`, `TehtavapankkiNotFoundError`) — and **never** by returning `ResponseEntity.notFound().build()`, which sends a bodiless 404 and shows the virkailija a blank page. `GlobalControllerExceptionHandler.handleServerException` matches the **base type**, so a new domain needs no change there; the `@ExceptionHandler(Throwable)` advice wins over Spring's own `@ResponseStatus` resolution, so an exception outside that hierarchy would drop into the `else` branch and render the **500** page instead of 404. The base class carries `@ResponseStatus`, and the `reason` goes to the exception message; neither reaches the user (the handler renders `ErrorPage.notFound`, i.e. `UiText.Error.sivuaEiLoydy`), so it only documents intent in logs/traces. `ResponseEntity<Void>` endpoints (e.g. tehtäväpankin `/lataa`-uudelleenohjaus) throw the same way — the advice produces `text/html` regardless of the handler's declared return type. Machine-readable endpoints (`produces = ["application/json"]`, e.g. the `koski-request` debug routes) **deliberately keep** the bodiless 404; don't "fix" those. `EiLoydyVirhesivuTest` pins the HTML routes and guards the JSON exception.
- **Display tables & CSV export (`html/table/*`)**: a list view and its CSV download share one column source — an enum implementing `RenderableDisplayTableEnum<T>` (e.g. `YkiSuoritusColumn`, `VktSuoritusColumn`), where each entry supplies `entityName`, `uiHeaderValue: LocalizedString`, `urlParam`, a `getValue: (T) -> String` (the CSV/text cell) and an optional `renderHtml` (overrides the HTML cell). **Which columns appear in HTML vs CSV is decided purely by `@ColumnTags(...)`, and the two are independent include-tags**: the HTML table selects `LIST_VIEW` (`DisplayTableColumn.of<C,T>(setOf(ColumnTag.LIST_VIEW), excludeTags)` in the `*Page`), while the CSV export selects `CSV_EXPORT` — **hard-coded** inside `DisplayTableCsvRenderer.renderCsv` (via `csvAttachmentResponse<C,_>`). So to add a column to the **CSV only**, annotate it `@ColumnTags(ColumnTag.CSV_EXPORT)` **without** `LIST_VIEW` (and vice-versa; a column can carry both, one, or neither). The filter itself is `RenderableDisplayTableEnum.getByTags` (`html/table/DisplayTableEnum.kt`): keep iff the entry's tag set intersects `require` **and** does not intersect `exclude`. The remaining `ColumnTag`s are request-driven **exclude** toggles applied to both paths, computed by `*SuorituksetParams.excludeTags()`: `PERSONAL_DATA` (dropped when "piilota henkilötiedot"), `OBSOLETE` ("piilota vanhentuneet tiedot"), `VERSION_HISTORY_ONLY` (kept only in the version-history view). CSV column **order = enum declaration order**; headers come from `uiHeaderValue` and follow the UI language (see i18n gotcha #2). All rows are read from the already-materialized entity `T`, so a new column that only reads existing entity fields needs no DB/SQL/service change — just the enum entry (+ a `UiText` header label).
- **Localization (i18n)**: FI/SV/EN. `LocalizedString(fi, sv, en)` (`i18n/LocalizedString.kt`) is the multilingual primitive for **both** koodisto reference data (loaded fi/sv/en from the koodisto service via `Translations`/`LocalizationService`) and static UI chrome. UI chrome lives in the typed catalog `i18n/UiText.kt`, where each entry is `tr("dotted.key")` — a computed getter (or a function that `.interpolate("count" to n)`s a `{count}` placeholder for parameterized strings). **`UiText.kt` holds only keys: there is no Finnish text in Kotlin.** The Finnish source text lives in the checked-in resource `server/src/main/resources/lokalisointi/fi.json` (with `sv.json`/`en.json` alongside it), which is loaded from the classpath in **every** profile. All three languages are additionally resolved at runtime from **Tolgee** via OPH's lokalisointi proxy (see "Tolgee sourcing" below), and the live value wins **per language** over the checked-in one. **No** Spring `MessageSource`/`messages*.properties` — do not add them. `LocalizedString.get(lang)` returns the requested language, **falling back to `fi`** (then, for a catalog string, the **key itself**; then the literal `"<invalid LocalizedString>"`) when that language is missing — so a half-migrated page renders untranslated bits in Finnish rather than blank; this is what makes package-by-package migration safe. `toString()` resolves the **ambient** `CurrentLanguage` (it is defined as `get(CurrentLanguage.get())`), so plain string interpolation and `+` emit the current UI language. The active language is resolved **ambiently**, not threaded: a `CookieLocaleResolver("kitu_lang")` + `LocaleChangeInterceptor(paramName="lang")` (`i18n/LocalizationConfig.kt`, bean **must** be named `localeResolver`) sets Spring's `LocaleContextHolder`, and `CurrentLanguage.get()` (`i18n/CurrentLanguage.kt`, a plain `object` — **not** a `@Service`, to avoid the `@WithSpan` CGLIB trap) reads it, defaulting to FI when no request is bound. Renderers emit a translated string by writing `+someLocalizedString` directly inside a tag block (e.g. `strong { +it.title }`), via the sole helper in `i18n/HtmlLocalization.kt`: `operator fun LocalizedString.unaryPlus()`. It's a `context(tag: Tag)` function — this is why `pom.xml` enables the `-Xcontext-parameters` Kotlin flag — and, like any extension, it must be **imported** (`import fi.oph.kitu.i18n.unaryPlus`) in each file that uses it. (There is deliberately no `t()`/`l()` helper and no Spring `MessageSource`; if you need the raw `String` — e.g. for an HTML attribute — call `someLocalizedString.toString()` (which resolves the ambient `CurrentLanguage`; pass an explicit `.get(lang)` only when you need a specific language).) `object`/static-`val` renderers (`html/Page.kt`, `html/Navigation.kt`) need no signature changes. The `html/Common.kt` article helpers are named **`errorMessage(LocalizedString)` / `warningMessage(LocalizedString)`** — not `error`/`warning` — precisely because a `FlowContent.error(String)` would let an accidental `error("literal")` silently resolve to Kotlin's stdlib `kotlin.error(Any): Nothing` (throws at runtime) instead of rendering an article. Keep those names distinct from `kotlin.error`. A **new** UI string is two lines: the key in `UiText.kt` and the Finnish in `lokalisointi/fi.json` (`UiTextTest` fails if you forget either). `LocalizedString(fi = "…")` remains correct for text that is _not_ catalog chrome — koodisto/organisaatio values and ad hoc strings — which never goes through `TolgeeMessages`. **Tolgee sourcing:** `tr(key)` returns `LocalizedString.withTolgeeKey(key)` — the object carries **only** the Tolgee key and resolves fi/sv/en **lazily** from `TolgeeMessages` on each `get()`/`toString()`/`interpolate()`/`contains()` (the key is a `private var` outside the data-class ctor, so `copy` ignores it; `equals`/`hashCode` are **hand-written to include it**, because every catalog string now has null fi/sv/en and would otherwise compare equal to every other one). Because resolution is lazy, a value stored in a `val` (e.g. a column-enum `uiHeaderValue`) **no longer freezes** — it tracks `LokalisointiScheduledTasks` refreshes, so the computed-getter / `when`-getter ceremony below still works but is no longer strictly required to avoid the freeze. When the store is empty or a key/locale is missing, `get()`'s fi fallback yields Finnish. `TolgeeMessages` (`i18n/TolgeeMessages.kt`) is a plain `object` with **two layers**: the _source texts_ read from the classpath (`lokalisointi/{fi,sv,en}.json`) during class initialization — deliberately **not** an `ApplicationRunner`, since runners execute only after the connector is already accepting requests — and the _live_ layer filled by `LokalisointiLoader`. The two are merged **per language** (`elava.fi ?: lahde.fi`, etc.) and the result is precomputed on write so `get()` stays one map lookup on the render hot path; a key-level replace would wipe the checked-in Swedish for keys whose live row carries only Finnish. `clear()` drops **only** the live layer, so `POST /kaannokset/tyhjenna-valimuisti` can never leave the UI without text. `setSourceTexts`/`reloadSourceTexts` exist for tests, which must restore **both** layers in `@AfterEach`. The store is filled at startup by `LokalisointiLoader` (an `ApplicationRunner`) which calls `LokalisointiClient` — it GETs flat per-locale JSON `/lokalisointi/tolgee/{namespace}/{locale}.json` from `https://{opintopolkuHostname}` and merges fi/sv/en into `Map<key, LocalizedString>`. `LokalisointiScheduledTasks` re-fetches on a db-scheduler interval (`kitu.lokalisointi.scheduling.*`). The cache can also be dropped by hand from the home page's Ylläpito card — `POST /kaannokset/tyhjenna-valimuisti` (`i18n/LokalisointiViewController`) clears `TolgeeMessages` and immediately reloads it, so a translator's change is visible without waiting for the interval. The controller is **unconditional** and takes the loader as an `ObjectProvider`, because the `LokalisointiLoader` bean does not exist when `kitu.lokalisointi.namespace` is empty (test/e2e/`local-opintopolku`) — there the route still clears the store and reports that lokalisointi is off. The **entire** lokalisointi machinery (client, RestClient config, loader, scheduled task) is gated by `@ConditionalOnNonEmptyProperty("kitu.lokalisointi.namespace")` — set in untuva/qa/prod only (`namespace=kielitutkintorekisteri`; the Tolgee **namespace** separates each app's translations in the shared lokalisointi service, cf. KOSKI's `koski`); in test/e2e/`local`/`local-opintopolku` the beans don't exist and the live layer stays empty, so everything renders from the checked-in `lokalisointi/*.json`. **`local` deliberately no longer fetches live**: untuva's proxy is ~160 keys behind and publishes no sv/en, so per-language merging would let its stale Finnish override fresher checked-in text. Translations are refreshed on demand with `python3 scripts/fetch_kaannokset.py` (defaults to the **QA** proxy, the only one carrying sv/en and the translator edits), reviewed as a git diff. The script never _adds_ keys — `fi.json` owns the key set — and editing an existing Finnish string there is pointless because Tolgee's `resolution: NEW` means it is overwritten on the next fetch; rename the key instead. Fetch failures never fail startup (the loader `runCatching`s and logs). No secret — the proxy serves published files. **Writing keys back to Tolgee (`i18n/tolgee/`)** — note this is a _different service_ from the read path: the lokalisointi proxy is read-only and has **no delete route**, so writes go **straight to Tolgee Cloud** (`https://app.tolgee.io`, `X-API-Key`). `tr` records each **key** (no text) into `UiTextRegistry`, and `TolgeeSyncService` takes the source text it pushes from `TolgeeMessages.sourceText(key)`, i.e. from `fi.json` — the source-text layer must never feed the registry, or QA would push Tolgee's own text back as source; `UiTextWarmup` (unconditional `ApplicationRunner`, `@Order(0)`) — both of those two files live in `i18n/`, **not** in `i18n/tolgee/`, which holds only the client/sync side — reflectively invokes every `UiText` member returning `LocalizedString` — properties, zero-arg functions, and functions whose params are all `Long` (called with `0L`s) — so the registry is complete regardless of what's been rendered. Then `TolgeeSyncRunner` (`@Order(100)`) diffs the registry against Tolgee's namespace and **creates missing keys and hard-deletes orphans**. Consequences worth knowing: (1) the warmup now **throws at boot** if any `LocalizedString` member can't be called (an uncallable member would look like a deleted key and get purged from Tolgee, losing translator work) — a `UiText` function taking a non-`Long` param is therefore a **startup failure**, in every profile including tests — **and it additionally throws if any `UiText` key is missing from `fi.json`**, since that key would otherwise render as a raw key string; because that check reads the global `UiTextRegistry`, a test that records a synthetic key into it breaks startup for every later test, so test catalogs must keep their fixtures out of the registry (see `UiTextWarmupTest`). `UiTextTest` pins the two key sets as **equal in both directions**, which is what keeps `UiText.kt` and `fi.json` from drifting; (2) the whole `tolgee` package is gated on `@ConditionalOnNonEmptyProperty("kitu.tolgee.apiKey")`, and the secret is injected **only into the QA task** (`props.name === "qa"` in `service-stack.ts`), so the secret's existence _is_ the environment restriction — there's no profile check; (3) deletes are capped by `max(kitu.tolgee.sync.minDeleteAllowance, maxDeleteRatio × Tolgee key count)` (default `max(5, 10%)`) — over the cap, creates still run, deletes are skipped, and the home page shows a warning driven by `TolgeeSyncStatus.last` (`tolgeeSyncWarning()`, a top-level `FlowContent` extension in `webmvc/HomePage.kt`); (4) `resolution: NEW` means an existing Tolgee source text is never overwritten — and since `get(FI)` prefers Tolgee's fi, a Finnish string edited in Tolgee keeps winning over the code no matter how you change the `tr(...)` literal, so **rename the key when a Finnish string's meaning changes**; (5) `kitu.tolgee.sync.dryRun=true` logs the diff without writing. `TolgeeClient` is an interface (impl `TolgeeClientImpl`) purely so tests can fake it with `object :` — this repo has no mocking library. Gotchas: (1) `Navigation.mainNavigation` **must stay a computed `val … get()`** (not a stored `val`): it references `UiText.Nav.*`, and a stored `val` would freeze those at class-load (before Tolgee loads), pinning the nav to Finnish; the getter rebuilds the list per render so it picks up loaded translations. (2) Table/CSV column headers are `DisplayTableEnum.uiHeaderValue: LocalizedString` (not `String`), resolved via `CurrentLanguage` in **both** the HTML table and `DisplayTableCsvRenderer` — so CSV **follows the UI language** (the old `.language(Language.FI)` pin in `VktSuoritusService.findEnrichedForCsv` was removed). CSV is served via `StreamingResponseBody` on an async thread where `LocaleContextHolder` is **unbound**, so `csvAttachmentResponse` captures the request language and re-binds it there with `CurrentLanguage.withLanguage(lang){…}` — without that, headers/enums would resolve to FI while koodisto cell values (resolved on the request thread) follow the UI language, giving a mixed-language file. If you ever need a fixed-language CSV again, re-pin `.language(...)` on the `translationBuilder()` and drop the `withLanguage` wrap. (3) There is no language-switcher UI yet, but the default UI language **follows the virkailija's Opintopolku `asiointikieli`**: Otuva CAS does **not** release the user's language (its attribute set is fixed — `oidHenkilo`/`idpEntityId`/`kayttajaTyyppi`/`roles`/`sessionindex`), so `CasUserDetailsService` fetches it from ONR (`getHenkiloByHenkiloOid(oid).asiointiKieli.kieliKoodi`, `getOrNull` → FI on failure) **once at login** and stores it on `CasUserDetails.asiointikieli`; `LocalizationConfig` feeds it as the default via `CookieLocaleResolver.setDefaultLocaleFunction { … }` (Spring 7 **removed** the overridable `determineDefaultLocale` — `setDefaultLocaleFunction` is its intended replacement) **only when no `kitu_lang` cookie is set**. Precedence: explicit `?lang=` (cookie) **>** Opintopolku `asiointikieli` **>** FI. Wiring the ONR dep meant injecting the `CasUserDetailsService` **bean** into `CasConfig` (it previously `new`ed a no-arg instance). The `?lang=`/cookie plumbing already works. Migration status — **nearly the whole virkailija HTML UI now resolves through `UiText`**: shared chrome (`Page`, `Navigation`, `ErrorPage`, `ErrorsArticle`, `Time`), the shared table/filter/CSV framework (`html/table/*`), the **`vkt`, `yki`, and `kotoutumiskoulutus` suoritukset views** (pages, column headers, filters, infoTable labels), the whole **YKI-arvioijarekisteri** UI (`yki/arvioijat/*`), the error and KOSKI-error views, `YkiTarkistusarvioinnitPage`, `html/FormErrors.kt`, and the koto **tehtäväpankki** pages (`kotoutumiskoulutus/koealusta/tehtavapankki/*` — incl. the ~32 Moodle question-type + ~34 metadata + language-name labels; the `moodleTehtavatyyppiNimet`/`languageLabels` `mapOf` lookups were rewritten as call-time `when`-functions returning `UiText.Koto.*`, since a top-level `val` map would **freeze** the translations at class-load). The etusivu kojelauta (`webmvc/HomePage.kt`) also resolves through `UiText`: its card titles and row labels take `LocalizedString`, not `String` — `statRow`/`actionRow`/`lazyCard` reuse `UiText.Nav.*` where the label **is** the nav item (so the dashboard and the menu can't drift apart, and Tolgee keeps one key per concept) and take the dashboard-only strings from `UiText.Etusivu.*`. Two bits of that file stay Finnish on purpose: the `tolgeeSyncWarning` diagnostics, and the `loaderScript` fallback message, which is a literal inside a generated JS string and would need escaping before it could hold arbitrary translated text. **Still un-migrated, and not deliberately so — just not done yet:** `html/SuoritusListPage.kt`, `html/KoskiErrorsPage.kt`. Don't read their Finnish literals as a decision. **Enum display values are localized too**, via the same class-load-freeze fix: `Arviointitila`/`TutkinnonOsa` `viewText` and `VktArvioinninTila` `nimi` were changed from enum-constructor `val`s to **computed `get() = when(this){ … -> UiText.X }`** properties (call sites reading `.viewText`/`.nimi` are unchanged). `viewText` ends in `.toString()` because it is typed `String`; `VktArvioinninTila.nimi` returns the `LocalizedString` itself, so it has no `.toString()`. Other localized enums: `Sukupuoli`, `Tutkintokieli`, `Tutkintotaso`, `Rekisterointitila`, `Turvakieltotieto`, and `YkiViewController.ONR_UNAVAILABLE_WARNING` became a computed `val get()`. **This `when`-getter is the standard recipe** for any enum/companion display `val` you want translated. Still hardcoded Finnish, deliberately: `*ApiController` OpenAPI + API-response error strings (external-API audience); `Arvosana.arvosana` (a `@get:JsonValue` **serialization** value, not pure display — must stay a fixed string); and koodisto `nimi` (loaded multilingually from the koodisto service via `LocalizationService`/`Translations`, a separate mechanism).
- **Typed errors**: Arrow's `arrow.core.Either<E, V>` (left = error, right = value) is the project's convention for propagating domain errors out of services — prefer returning `Either` over throwing. Project-specific helpers live in `util/result/EitherExtensions.kt` (`getOrThrow` and `splitIntoValuesAndErrors`). `Either.fold(ifLeft, ifRight)` (note: ifLeft is the **first** named arg, opposite of the legacy `TypedResult.fold(onSuccess, onFailure)` order — always use named args).
- **Validation**: validators implement `Validation<T>` (`util/validation/Validation.kt`) — a three-phase pipeline of `validateBeforeEnrichment` → `enrich` → `validateAfterEnrichment` run by `validateAndEnrich`. The two `validate*` phases use the `ValidationRaise` typealias (= `Raise<NonEmptyList<ValidationError>>`) as their receiver and return `Unit` — the type system thus prevents transforming the value inside them. The sibling typealias `ValidationResult<T> = Either<NonEmptyList<ValidationError>, T>` covers the Either-shaped result. All transformation/derivation lives in `enrich`, whose receiver is the narrower `EnrichmentRaise` (= `Raise<ValidationError.EnrichmentError>`) — it may fail, but only with a single enrichment error, not an accumulated list. Checks that depend on the post-enrichment shape go in `validateAfterEnrichment` — see `YkiSuoritusValidation` where `enrich` optionally recomputes `arviointitila` via `laskeArviointitila` (only when `kitu.yki.convertLegacyArviointitila.enabled`, else passes the value through unchanged) and `validateAfterEnrichment` enforces "at least one osakoe" (`validateOsakokeitaOnAtLeastOne`, on the raw `osat`) plus that the arviointitila matches the arvosanat (`validateArviointitilaVastaaArvosanoja`). Compose sub-validators inside an `accumulate { … }` block (from `arrow.core.raise.accumulate`, `@OptIn(ExperimentalRaiseAccumulateApi::class)`), wrapping each call in `accumulating { … }` so all errors are collected in parallel rather than short-circuiting. Use `mapOrAccumulate` over collections, and `ensure` / `ensureNotNull` for predicates. Sub-validators that themselves accumulate take `RaiseAccumulate<ValidationError>` and nest further `accumulating { … }` blocks inside. Controller boundary uses `validation.validateAndEnrich(…).orThrowBadRequest()` (extension in `ValidationService.kt`) which throws `ValidationException(NonEmptyList<ValidationError>)` — the name deliberately differs from `util/result/EitherExtensions.kt`'s `getOrThrow`, which rethrows the Left and ends up a **500**, so importing the wrong one would silently swap the status code — caught by `GlobalControllerExceptionHandler` and turned into a 400.
- **Observability**: Spring's `spring-boot-starter-opentelemetry` + an explicit `opentelemetry-spring-boot-autoconfigure` dep (the latter supplies the `@WithSpan` aspect that Spring's starter drops). Traces exported OTLP to Jaeger locally (`docker-compose.yml` exposes UI on `:16686`). **Gotcha:** `@WithSpan` makes the bean a CGLIB proxy. A `@WithSpan` method **inherited from an abstract base class** reads that base class's constructor-injected fields as `null` at runtime (the proxy delegates the call in a way that skips the base-class field init), even though the same method+field on the concrete `@Service` works fine. So don't push injected dependencies (`Tracer`, repositories, `AuditLogger`) into an abstract base service — keep them on the concrete class and extract shared logic into top-level helper functions that take the deps as params (see `csvparsing/CsvExportErrorHelpers.kt` — one function, `getCsvExportErrorsSorted`, with `YkiSuoritusErrorService` as its only caller; `YkiArvioijaErrorService` is gone, `yki_arvioija_error` was dropped in V116). **Toinen ansa — `Span.current()` ei ole HTTP-span:** kontrollerin rungossa ajossa oleva span on Spring Securityn `secured request` -observaatio (INTERNAL), **ei** SERVER-span. Spanipuu yhdelle pyynnölle on `kitu` (SERVER-segmentti: `uri`, `method`, `status.code`) → `secured request` (INTERNAL) → `@WithSpan`-metodit. Joten `Span.current().setAttribute(...)` kontrollerissa kirjoittaa attribuutin eri lokiriville kuin se, jolla reitti näkyy. Tällä on väliä, koska **CloudWatch Logsin metriikkasuodin tutkii yhden lokirivin kerrallaan**: `aws/spans`-suodin, joka vaatii sekä `$.attributes.uri`n että kontrollerin asettaman attribuutin, ei täsmää koskaan — ja vikaantuu hiljaa, koska `treatMissingData: NOT_BREACHING` tekee emittoimattomasta metriikasta erottamattoman siitä ettei mitään tapahtunut (näin `PostYkiSuoritus` oli nollissa 4.6.–16.9.2026). Suodata siis kontrollerin omaan attribuuttiin, älä yritä yhdistää kahden spanin kenttiä, ja **validoi suodinlauseke oikeaa dataa vasten** `aws logs test-metric-filter`illa ennen deployta. Muista myös ettei suodinlauseke voi viitata pisteellisiin JSON-avaimiin, joten attribuuttien nimien on oltava pisteettömiä.
- **RestClient message converters**: configure via the SB4 DSL `configureMessageConverters { cs -> cs.registerDefaults()... }`, not the deprecated `messageConverters(...)`. Use `withJsonConverter(JacksonJsonHttpMessageConverter(mapper))` to swap Jackson, and `configureMessageConvertersList { list -> list.add(0, x) }` when ordering matters. Any `RestClient` that reads a JSON body into `String` (including `retrieveEntitySafely(String::class.java)`) must call `.withLenientStringConverter()` from `restclient/RestClientExtensions.kt` — Spring 7's default `StringHttpMessageConverter` only advertises `text/*`, so without the helper the call fails inside Jackson.
- **Spring HATEOAS 3 `linkTo` DSL**: tracks the controller invocation via the lambda's **return value** (not a thread-local), so the lambda signature must be `(C) -> Any`. A `C.() -> Unit` receiver lambda collapses to `Unit` and bypasses the proxy's `LastInvocationAware` tracking — see `html/Navigation.kt`.
- **Testcontainers 2.x**: artifacts are prefixed (`testcontainers-postgresql`, `testcontainers-junit-jupiter`) and `PostgreSQLContainer` moved to `org.testcontainers.postgresql.PostgreSQLContainer` (no generic parameter). On macOS set `DOCKER_HOST="unix://${HOME}/.docker/run/docker.sock"` if the socket isn't auto-detected.

- **Lambda runtimes are never pinned, and orphan stacks are the hazard**: the one Lambda the repo owns (`koski-audit-logs-integration-stack.ts`) uses `Runtime.NODEJS_LATEST`, and CDK's own custom-resource Lambdas use `determineLatestNodeRuntimeName()` — both _variable_ values that move when `aws-cdk-lib` is bumped. Renovate automerges those bumps and every `main` push redeploys, so runtimes stay current by themselves; **do not pin a runtime to "fix" a deprecation warning**. What actually goes stale is a CloudFormation stack that was renamed or deleted in code but never deleted in AWS: CDK stops managing it and its resources freeze forever (this is where every `nodejs20.x` Lambda in this project came from — `Prod-AlarmsStack`, `CertificateStack`, and the writer left behind in the legacy `DnsStack`). **When you remove or rename a stack, delete the old CFN stack in every account in the same change.** `infra/scripts/audit-deployed-stacks.sh` (run weekly by `.github/workflows/aws-audit.yml`) diffs deployed stacks and Lambda runtimes against the synthesized app and reports the drift; `alarms-stack.ts` additionally forwards `aws.health` `scheduledChange` events to Slack so EOL notices are seen. Two related traps: `PhysicalName.GENERATE_IF_NEEDED` on the alarms SNS topics is what keeps the us-east-1 ↔ eu-west-1 sharing free of `crossRegionReferences` (removing it re-materializes a pair of custom-resource Lambdas per stack), and the per-env `DnsStack` that owns the Route53 zone is _deliberately_ outside the CDK app — the in-app `<Env>/Dns` only does `HostedZone.fromLookup` and synthesizes to an empty stack.

### Deployments

`main` pushes auto-deploy through `.github/workflows/build.yml`. Full chain: `verified_in_queue` → `server_tests ∥ frontend_tests ∥ lint ∥ infra_lockfile ∥ build_image` (pushed to the `Util` account ECR) `∥ deploy_util ∥ submit_dependencies` → `deploy_dev` (waits for both the image and the tests) → `deploy_test` → `deploy_prod` → `build_docs` (GitHub Pages). **Tests are skipped on main when the merge queue already passed the same SHA**: the queue fast-forwards main to exactly the commit it tested, so `verified_in_queue` reads the commit's check runs and outputs `verified=true` when all four test/lint checks are `success`/`skipped` there; a direct push to main runs everything. On PRs and in the queue, `server_tests`/`frontend_tests` are additionally skipped by `list_changes`' `server`/`e2e` path filters (infra-only, docs-only, scripts-only changes). Since any of those may be skipped, every deploy job's `if:` checks `!cancelled()` plus the direct dependency's `result == 'success'` explicitly — a bare implicit `success()` would let a skipped upstream job silently skip the whole deploy chain. PR runs cancel superseded ones via workflow-level `concurrency`; on main and in the queue the group is per-run on purpose (a shared group would replace a pending main run and skip its deploy). The four deploy jobs all call `_deploy-env.yml`; **`deploy_util` is a real job that `deploy_dev` depends on** — don't omit it. The `lint` job runs `check-formatting.sh` _and_ `check-workflows.sh`. On PRs, `determine_action` flips the action to `diff` and posts a `cdk-notifier` comment instead of deploying. Four AWS accounts (`infra/lib/accounts.ts`): dev `682033502734`, test `961341546901`, prod `515966535475` — these three are in the README — plus the shared utility account `961341524988`, which is not.

**Renovate ja `infra/package-lock.json`:** Renovate ei osaa päivittää lockia `aws-cdk-lib`ille (ainoa `bundleDependencies`-riippuvuus), vaan jättää `renovate/artifacts`-statuksen punaiseksi ja avaa PR:n jossa on muuttunut **vain `infra/package.json`**. Kerran desynkatussa puussa myös `aws-cdk`-nostot epäonnistuvat samalla tavalla, ja `npm ci` kaatuu vasta mainissa. `^`-alueelliset riippuvuudet (aws-sdk-js-v3 yms.) eivät kärsi tästä, koska Renovate päivittää niiden lockin omalla `updateLockedDependency`-koodillaan ajamatta npm:ää lainkaan. Kaksi toisiaan täydentävää suojaa: `skipInstalls: false` (täysi `npm install` `--package-lock-only`:n sijaan, jolloin niputetut riippuvuudet resolvoituvat) ja `Infra lockfile in sync` -työ **pakollisena** tarkistuksena repon rulesetissä — jälkimmäinen on se joka tosiasiassa pysäyttää desynkan, sillä se kaataa `npm ci`:n jo PR:ssä. **Älä lisää `renovate/artifacts`ia pakolliseksi tarkistukseksi** — ihmisten PR:t eivät koskaan saa sitä ja jäisivät ikuisesti jumiin. Huom: `platformAutomerge` oli aiemmin `false` kolmantena suojana (Renovate mergeää vasta kun _jokainen_ tarkistus on vihreä, GitHubin oma automerge odottaa vain pakollisia), mutta merge queuen myötä se **on pakko olla `true`** — ks. alla.

**Merge queue:** mainiin ei mergetä suoraan vaan rulesetin merge queuen läpi (`rebase`, 1–5 entryä, ALLGREEN). Syy: `rebaseWhen`in oletus `auto` = `behind-base-branch` kun automerge on päällä, joten jokainen mainiin tuleva commit nollasi kaikkien Renovate-haarojen tarkistukset — vihreä ikkuna ~14 min, Renovaten ajoväli ~28 min, eli PR:t mergeytyivät käytännössä vain öisin. Jono testaa entryn **mainin kärkeä vasten** ennen mergeä, joten `rebaseWhen: "conflicted"` on nyt turvallinen (aiemmin se hylättiin juuri siksi, ettei vanhentunutta haaraa testattaisi yhdessä uusien versioiden kanssa — merge queue poistaa tuon riskin). Kaksi asiaa joita **ei saa rikkoa**: (1) `build.yml`illa on oltava `merge_group:`-triggeri, muuten pakolliset tarkistukset eivät raportoi jonossa lainkaan ja entry **aikakatkeaa 60 min päästä** — eli mikään ei mergeydy; (2) `platformAutomerge: true`, koska jonon takana Renovaten oma REST-merge hylätään ("Changes must be made through the merge queue") — GitHubin natiivi automerge on se joka asettaa PR:n jonoon. Jonoajossa `github.ref_name` on `gh-readonly-queue/main/...`, ei `main`, joten deployt ja ECR-push eivät laukea; `list_changes` ajaa `paths-filter`in jonossakin (se vertaa `merge_group.base_sha..head_sha`, eli kaikkea mitä entry ja sitä edeltävät tuovat mainin päälle), mutta `image`, `infra` ja `mise` pakotetaan jonossa `true`ksi, jolloin `build_image` oikeasti ajetaan jonossa mutta ilman pushia, ja `deploy_util` on erikseen estetty `github.event_name != 'merge_group'` -ehdolla.

## Conventions

- **Language**: user-facing text, commit messages, and PR titles are in Finnish. Kotlin/TS identifiers are Finnish/English mix following existing usage in the touched package — follow the surrounding file.
- **Formatting**: ktlint (K2 mode, format-on-save in IDEA) for Kotlin; prettier for TS/JSON/YAML/MD; shellcheck for `scripts/*.sh` and `infra/scripts/*.sh`. `.git-blame-ignore-revs` tracks formatting-only commits — add new bulk-reformat commits there.
- **Always run `./scripts/format.sh` before reporting a task done** whenever TS/JSON/YAML/MD (or Kotlin) files have been touched. The script runs `prettier --write .` and `ktlint --format`, matching what `check-formatting.sh` enforces in CI.
- **Banned dependencies**: `pom.xml` enforces exclusions for vulnerable `bouncycastle` and `xmlunit-core` versions; don't let transitive updates reintroduce them.
- **Keep `infra/README.md` accurate**: any change under `infra/lib/` or `infra/bin/` that affects which stacks exist, what they create, IAM identities, cross-account wiring, manual prerequisites (DNS zones, secrets, KOSKI-side resources), or the Slack/alarms/investigation flow must update `infra/README.md` in the same commit.
