# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Kielitutkintorekisteri (kitu) — OPH's register for language-exam data. Virkailija-facing Spring Boot app that also forwards records to the KOSKI service so they can be shown to citizens in Oma Opintopolku. Primary documentation and external API descriptions are linked from `README.md`.

## Toolchain

Tool versions live in `.mise.toml` and are installed automatically by `scripts/start_local_env.sh`: Java (corretto), Node, Maven, ktlint, prettier, shellcheck, actionlint, aws-cli, go, `cdk-notifier` (PR diff comments in `_deploy-env.yml`), humanlog. **Kotlin and the Java release are _not_ in `.mise.toml`** — they live in `server/pom.xml` as `kotlin.version`/`java.version`. Read exact versions from those two files rather than restating them here; Renovate bumps them continuously. `AWS_PROFILE=oph-ktr-dev` and `SPRING_PROFILES_ACTIVE=local` are set by mise.

## Common commands

```shell
# One-shot dev env setup (installs mise deps, Playwright browsers, starts tmux with db+server).
# Pulls secrets from AWS Secrets Manager via the oph-ktr-dev profile.
./scripts/start_local_env.sh
./scripts/start_local_env.sh --setup-only   # skip tmux/containers

# Run the server standalone after the DB is up (wraps mvnw spring-boot:run + humanlog).
./scripts/start_local_server.sh

# Just the DB, Jaeger and LocalStack (S3)
docker compose up -d

# Backend build/test (in server/)
./mvnw package               # full build with tests
./mvnw test                  # tests only
./mvnw test -Dtest=OidTest   # single test class
./mvnw test -Dtest=OidTest#methodName

# Formatting (ktlint + prettier + shellcheck). CI runs the same script.
./scripts/check-formatting.sh
./scripts/format.sh          # auto-fix

# E2E Playwright (in e2e/)
npx playwright test
npx playwright test --ui
TEST_WORKERS=4 npx playwright test   # default 1, no cap in config; each worker boots its own server on 8080+index (CI forces 1)

# Infra (in infra/)
npm run diff/dev     # these pin TAG to `git rev-parse main` and pass --exclusively
npm run deploy/dev
TAG=$(git rev-parse main) npx cdk deploy --exclusively 'Dev/**'   # equivalent to the above
```

Backend tests spin up PostgreSQL via Testcontainers — Docker must be running. The Playwright suite expects the app's Maven build to launch it; see `e2e/README.md` for how to attach to an already-running IDEA debug session (`reuseExistingServer: true`).

**After switching branches, run `./mvnw clean` first.** Flyway reads migrations from the classpath (`target/classes/db/migration`), and neither Maven nor the Kotlin compiler deletes class/resource files whose source has disappeared — so a migration belonging to another branch keeps running against every fresh Testcontainers database. The symptom is a `column "…" does not exist` failure in tests the source tree says should pass.

## Architecture

### Layout

- `server/` — Spring Boot 4 + Kotlin backend. Source roots are `src/main/kotlin` and `src/test/kotlin` (configured in `pom.xml`, not the Maven defaults). Packages under `fi.oph.kitu/` are organized by **feature domain**, not by layer.
- `infra/` — AWS CDK (TypeScript) app. `bin/infra.ts` wires four stages: `Util` (shared ECR repo via `container-repository-stack`, GitHub Actions roles, plus its own `alarms-stack` for ECR vulnerability notices), then `Dev`/`Test`/`Prod`. Every account — Util and each env — gets one `account-settings-stack` (account-wide S3 Block Public Access via an `AwsCustomResource`, because CloudFormation has no resource type for it; account-wide, so never put it in a stack that also exists in us-east-1). Each env stage composes stacks (`account-settings-stack`, `service-stack`, `db-stack`, `network-stack`, `connections-stack`, `alarms-stack`, `log-groups-stack`, `backups-stack`, `route53-health-checks-stack`, `koski-audit-logs-integration-stack`, `github-actions-stack`, `dns-stack`). There are **no Prod-only stacks**: `yki-historia-upload-stack` was removed once the YKI-historia migration had been run, as were `bastion-stack` and `ecs-rds-proxy-stack` in `253dc088` — don't go looking for any of them. `infra/README.md` documents all 13 stacks. Deploys pick the container by `TAG` env var.
- `e2e/` — Playwright tests against a real server + Postgres.
- `scripts/` — bash helpers for local env, AWS profile/secret setup, tmux orchestration.
- `docs/` — published to GitHub Pages. `docs/technical/` is hand-written prose (arkkitehtuuri, koodikonventiot, integraatiot, yllapito) rendered by Jekyll — `build.yml` hard-checks those pages exist. The rest is generated: DB schema diagrams via SchemaSpy (`docs/build.sh`) and component UML per environment (`docs/build-uml.sh`). `docs/db-scheduler/README.md` is hand-written.
- `.claude/skills/` — shared Claude Code skills: `verify` (boot the server on the `e2e` profile without AWS and drive it over HTTP) and `integraatiokaaviot` (the integration data-flow SVGs in `docs/technical/kaaviot/` are generated by its `kaaviot.py`; the skill covers checking for hand edits before regenerating).

### Feature domains (server packages)

Each domain typically contains its own `*ApiController`, `*ViewController` (server-rendered HTML via `kotlinx.html`), `*Service`, `*Repository`, entities, and `*ScheduledTasks`:

- `vkt/` — Valtionhallinnon kielitutkinnot
- **VKT:n uusintaan oikeutetut (`vkt/uusintaoikeus/`, OPHKOTO-177):** raportti `/vkt/uusintaoikeudet` (+ CSV `/api/vkt/uusintaoikeudet`) henkilöistä, joilla on tarkastelupäivänä oikeus uusia hylätty osakoe, henkilöt ja uusittavat osakokeet eroteltuina taitotasoittain. Säännöt elävät **yhdessä SQL-kyselyssä** (`VktUusintaoikeusRepository`), jossa OPH:n jokainen ehto on kommentoitu ("Ehto 1"…"Ehto 6") — kysely on määrittelyn toteutus, joten pidä kommentit sen tasalla. Se **ei** käytä `VktTutkinto`a eikä `VktOsakoePartitioning`ia: niiden 3 vuoden ikkunat ankkuroituvat taidon ensimmäiseen tutkintopäivään eivätkä mallinna uusintaoikeutta. Vahvistetut tulkinnat: (1) kolme vuotta lasketaan **ensimmäisestä** hylkäyksestä, eikä hylätty uusinta pidennä oikeutta — tutkintokerran määrää toisen osakokeen viimeisin hyväksytty suoritus, ja uusittavan osakokeen ensimmäinen hylkäys on sen suoritus, joka on ajallisesti lähimpänä sitä (sama tutkintokerta); (2) osakokeet ovat samaa tutkintoa vain, jos niiden tutkintopäivät ovat enintään 3 v päässä toisistaan; (3) myös ymmärtämisen taito lasketaan, ja kahden tutkinnon kautta uusittava osakoe on yksi rivi. Oikeus päättyy `LEAST(hylkäys + 3 v, 31.12.2028)` (`UUSINTAOIKEUDEN_VIIMEINEN_PAIVA`). Tarkastelupäivä on rajausdialogin `tarkastelupaiva`-parametri (tyhjänä `TimeService.today()`), ja **mennyt tarkastelupäivä on tilannekuva**: `osakokeet`-CTE ottaa mukaan vain osakokeet, joiden `arviointipaiva <= :tarkastelupaiva`, joten myöhemmin arvioitu hylkäys ei vielä synnytä oikeutta eikä myöhemmin arvioitu hyväksytty uusinta vielä kumoa sitä. Kieli- ja taitotasorajaukset tehdään muistissa (`VktUusintaoikeusParams.rajaa`) eivätkä kuulu määrittelyn SQL:ään. **CSV:hen haetaan yhteystiedot ONR:stä** (puhelin, sähköposti, kotiosoite eriteltynä), mutta vain kun henkilötietoja ei piiloteta — sarakkeet ovat `CSV_EXPORT` + `PERSONAL_DATA` ilman `LIST_VIEW`iä, eikä piilotettu vienti kutsu ONR:ää lainkaan. Haku on **yksi eräkutsu** `OppijanumeroService.getHenkilotByHenkiloOids` → `POST henkilo/masterHenkilosByOidList` (≤ 5000 OID:ia kerralla, vaatii `REKISTERINPITAJA(_READ)`- tai `HENKILON_RU`-roolin), koska henkilökohtainen `getHenkiloByHenkiloOid` tekee ~3 HTTP-kutsua per henkilö ja CSV rakennetaan ennen striimauksen alkua. Rajapinnan oletustoteutus kutsuu henkilöhakua yksi kerrallaan, joten `MockOppijanumeroService` ja testien anonyymit stubit toimivat sellaisenaan. Valintasäännöt ovat `oppijanumero/HenkilonYhteystiedot.kt`:ssä: osoite yhdestä ryhmästä järjestyksessä VTJ vakinainen kotimainen (`yhteystietotyyppi4`) → VTJ vakinainen ulkomainen (`5`) → kotiosoite (`1`); puhelin ja sähköposti henkilökohtaisista ryhmistä ensin ja työosoite (`2`) viimeisenä. Turvakieltoa **ei** suodateta (OPH:n päätös). **ONR-virhe ei kaada latausta**: CSV toimitetaan tyhjin yhteystietosarakkein ja virhe lokitetaan varoituksena — myös 403 näkyy vain näin. **1.1.2029 alkaen raportti on tyhjä**, ja silloin kaatuu myös `e2e/tests/vkt/vkt-uusintaoikeudet.spec.ts`, jonka kiinteät fixture-päivät nojaavat siihen — raportti on siinä vaiheessa tarkoitus poistaa.
- `yki/` — Yleiset kielitutkinnot (suoritukset + arvioijat). Records arrive from Solki as **JSON pushes** (`POST /yki/api/suoritus`, `POST /yki/api/arvioija`). The old Solki **CSV import pipeline was removed** — don't go looking for a parser: CSV is **export-only** (`csv/`). **Versiointi / muuttumattoman datan tunnistus:** every push appends a row to `yki_suoritus` (`unique_suoritus` = `(solki_id, last_modified)`, and `last_modified` is `Instant.now()` at ingest, so ON CONFLICT never dedupes). The only guard is `YkiSuoritusRepository.save`, which compares the incoming entity against `findLatestBySolkiIds(...)` via `equalsIgnoringAnnotated(..., "DB")` and skips the write when they match. **Any entity field kitu writes itself — and that Solki therefore never sends — must carry `@IgnoreForEquality("DB")`**, or it diverges after the first write and every later push appends a no-change version (this was the cause of the duplicate history rows in prod: `koskiOpiskeluoikeus`, `koskiSiirtoKasitelty`, `arviointitilaLahetetty`, `arviointitilanLahetysvirhe`, `tarkistusarviointiHyvaksyttyPvm`). **The trap:** ignoring a field also makes kitu's _own_ write of that field a no-op, so such call sites must pass `forceWrite = true` — see `KoskiService`. Two further normalizations run before the comparison so that what we compare is what actually round-trips: `withTallennettavaTarkistusarviointi` (a tarkistusarviointi is reachable only through `yki_osakoe_tarkistusarviointi`, so one with no linked osakoe is unstorable and gets dropped; empty `arvosanaMuuttui` reads back as SQL NULL) and `withHyvaksyttyTarkistusarviointi` (`TARKISTUSARVIOINTI_HYVAKSYTTY` is kitu's own tila, so an incoming `TARKISTUSARVIOITU` is promoted to it before comparing — otherwise a re-push would silently revert the virkailija's hyväksyntä). **Two query builders, pick by result size:** `YkiSuoritusSql.selectSuorituksetFull` appends the caller's `WHERE` after the `DISTINCT ON (solki_id)` CTE and aggregates arvosanat/tarkistusarvioinnit over the whole table, so a lookup that returns one suoritus still reads the entire register (~250 ms at prod size) and no index on the filtered column helps. Lookups that return few rows (Solki push via `findLatestBySolkiIds`, the yhteystiedot API, the KOSKI-siirto, tarkistusarvioinnit) therefore use `selectViimeisimmatSuoritukset(ehto)`, which pre-filters the `DISTINCT ON` with `solki_id IN (SELECT solki_id FROM yki_suoritus WHERE ehto)` — semantics are unchanged because the condition is still checked against the latest version — and computes the aggregates with `LATERAL` subqueries (< 1–11 ms). The condition may reference only `yki_suoritus` columns. **Don't use it for bulk reads** (list view, CSV, counts): per-row `LATERAL` is 3–10× slower than the one-pass hash aggregate there, and `COUNT(*)` can't drop a `LATERAL` join the way it drops the unused aggregate CTE.
- **YKI-arvioijarekisteri — tila lasketaan, ei talleteta:** `yki_arviointioikeus.tila` on **vanhentunut** (V121: nullable, ei defaultia). Kitu kirjoittaa aina NULLin ja tila lasketaan kauden päivistä `Rekisterointitila.laske`ssa (PASSIVOITU jos päättymispäivä < tänään, TULEVAISUUDESSA jos alkupäivä > tänään, muuten AKTIIVINEN; päättymispäivä on inklusiivinen). **Vain tallennettu `PASSIVOITU` ohittaa laskennan** — tallennettu `AKTIIVINEN` sivuutetaan, koska V117 täytti sarakkeen sillä eikä se kanna tietoa. Ainoa ei-tyhjän arvon kirjoittaja on Solkin push (`Tallennuslahde.SOLKI`). Sama sääntö on kirjoitettu kahdesti — Kotliniksi ja `Rekisterointitila.SQL`:ksi listanäkymän suodatusta ja lajittelua varten — ja `YkiArvioijaTilaSqlTest` on ainoa asia joka pitää ne yhtenevinä. Listakysely **kääritään alikyselyyn** (`SELECT * FROM (...) arvioijarivi`): ilman sitä `ORDER BY tila` kaatuu (`ORDER BY "tila" is ambiguous`) ja WHERE osuisi hiljaa vanhentuneeseen sarakkeeseen, koska aliakset eivät näy WHERE-lauseessa. Päivä sidotaan parametrina (`:tanaan`) `TimeService`ltä, **ei** `CURRENT_DATE`:na — muuten kiinnitetty testikello ei ohjaa SQL:ää. Seuraukset: passivointi **päättää kauden** tähän päivään (ja vain kiristäen — muuten klikkaus pidentäisi vanhentunutta oikeutta), joten merkintä lukee "Aktiivinen" passivointipäivän loppuun; passivointinappi näkyy ehdolla `passivoitu == null`, koska säilytysajan alkuhetki on saatava asetettua myös luonnollisesti päättyneelle merkinnälle; ja `jatkorekisterointi` johdetaan (`kaudenAlkupaiva > ensimmainenRekisterointipaiva`) eikä tule enää lomakkeelta.
- **YKI-arvioijarekisteri — arviointikausi on master, `yki_arviointioikeus` projektio:** kausi on **arvioijakohtainen**, ei kielikohtainen (OPH: _"henkilöllä ei ole päällekkäisiä arviointikausia vaan kaikilla sama kausi"_), ja elää V122:n `yki_arvioija_arviointikausi` + `..._oikeus` -tauluissa, joilla on pysyvä id. Virkailija lisää, muokkaa, passivoi ja poistaa kausia tietosivulta (`/yki/arvioijat/{id}/kaudet/**`). `yki_arviointioikeus` on **johdettu**: `Kausiprojektio` valitsee projisoitavan kauden (voimassa oleva > tuleva > viimeisin päättynyt) ja `YkiArvioijaKausiRepository.paivitaProjektio` kirjoittaa sen — **vain jos jokin arvo tosiasiassa muuttui**, muutoin yöllinen ajo leimaisi koko rekisterin muokatuksi ja lähettäisi sen uudelleen Solkiin. Näin `Rekisterointitila.SQL`, listanäkymä ja Solki-lähetys jatkavat ennallaan. Kolme ansaa: (1) valinta riippuu kuluvasta päivästä, joten projektio vanhenee kun tuleva kausi alkaa — sen korjaa `kitu.yki.scheduling.paivitaArvioijaProjektiot`, joka on **kytketty `integraatioKaytossa`-lippuun** — täysi sisääntuleva push kirjoittaa projektion koskematta kausimasteriin, joten taulut ovat taatusti eri linjoilla ja koko rekisterin yliajo vanhentuneesta masterista työntäisi sen lisäksi Solki-lähetysjonoon; (2) **säilytysaika ei saa lukea pelkkää projektiota** — `Sailytysaika.ALKUHETKI_SQL` ottaa `GREATEST`in projektiosta ja masterista ja `poistaSailytysajanYlittaneet` tarkistaa erikseen, ettei masterissa ole voimassa olevaa kautta, koska muuten vanhentunut projektio poistaisi yhä voimassa olevan merkinnän; (3) **arvioijatason passivointi katkaisee kaudet ennen `tallenna`a**, koska `tallenna` synkronoi kaudet oikeuksista — väärässä järjestyksessä syntyy uniikkiehdon rikkova duplikaattikausi. **Hallintopäätöksen ASHA-numero kuuluu kaudelle**, ei arvioijalle (V124): jokainen kausi on oma hallintopäätöksensä, joten arvioijatasolla jatkokausi olisi ylikirjoittanut edellisen viitteen. Numero kulkee myös projektioon, jotta listanäkymän haku, lajittelu ja CSV jatkavat ennallaan. Vanhentuneet kielet (`SWE10`, `ENG11`, `ENG12`) **eivät kuulu kausiin** lainkaan: ne jäävät jäädytetyiksi `yki_arviointioikeus`-riveiksi ja näkyvät tietosivulla omassa vain-luku-osiossaan. `yki_arvioija_kausi` säilyttää nimensä mutta on nyt pelkkä **muutosloki** (`toimenpide`-sarake, ei uniikkiehtoa) — uudelleennimeäminen rikkoisi rinnakkain ajossa olevan vanhan sovellusversion tietosivun. §2.4:n "kaikilla kielillä sama kausi" ja "uusi kieli perii voimassa olevan kauden" eivät ole validointisääntöjä vaan **rakenteellisia**: kaudella on yksi päiväpari ja N kielriviä.
- **YKI-arvioijarekisteri — integraatiokytkin ei koske käsin lähetystä:** `kitu.yki.arvioijarekisteri.integraatio.enabled` estää **automaattisen** lähetyksen Solkiin (tallennuksen jälkeinen synkroninen yritys, `lahetaLahettamattomat`, `SolkiArvioijaScheduledTasks` ja `paivitaArvioijaProjektiot`), mutta **ei** virkailijan tietosivulta painamaa "Lähetä uudelleen Solkiin" -painiketta: se kutsuu `SolkiArvioijaService.lahetaArvioijaKasin`ia, joka ohittaa kytkimen — yksittäinen lähetys on se tapa, jolla integraatiota kokeillaan ennen automaattisen liikenteen avaamista. Siksi `SolkiArvioijaClientImpl` ja `SolkiArvioijaServiceImpl` ovat **ehdottomia beaneja** — älä tee niistä ehdollisia, muuten lähetyskoneisto puuttuu kytkimen ollessa pois eikä painike toimi. Painike on silti **muokkauskytkimen** takana, koska POST-reitti on. Onnistunut käsin lähetys poistaa rivin lähetysjonosta ja epäonnistunut kirjaa `solki_lahetysvirhe`n normaalisti.
- **YKI-arvioijahakemukset atarusta (`ataru/` + `yki/arvioijat/hakemus/`):** eräajo hakee atarun arvioijahakemuslomakkeen hakemukset ja kutsuu niille `YkiArvioijaService.luoArvioija`a (`tekija = null`), joka ylikirjoittaa olemassa olevan arvioijan yhteystiedot ja lisää jatkokauden; kausi alkaa tänään tai voimassa olevan/tulevan kauden päättymistä seuraavana päivänä. Lomakkeen kartoitus on **ympäristökohtainen asetus** `kitu.ataru.arvioijahakemus.*` (`ArvioijahakemusLomake`, `@ConfigurationProperties`) tiedostossa **`arvioijahakemuslomake.yml`**, profiilikohtaisina YAML-dokumentteina: `lomakkeenAvain`, `kielikysymys`, `kielet.<vaihtoehdon arvo>.{kieli, tasokysymys, tasot.<vaihtoehdon arvo>: [PT, KT]}` ja `kentat.*` — jokaisessa ympäristössä on oma lomake, ja ataru generoi kenttien id:t ja vaihtoehtojen arvot lomakkeelle, joten niitä **ei saa kovakoodata**. **Tasot valitaan kielikohtaisesti** (jokaisella kielivaihtoehdolla oma jatkokysymys), ja yksi vaihtoehto voi antaa useita tasoja ("perus- ja keskitaso" = PT + KT). Vaihtoehtojen arvojärjestys vaihtelee kysymyksittäin, joten ei oleteta mitään järjestyksestä. QA:n kartoitus on lomakkeen nykytilan mukainen ja e2e/`local-opintopolku` jakavat mock-fixtuurin paikkamerkkikartoituksen; `ArvioijahakemusLomakeTest` sitoo jokaisen dokumentin ja vaatii sen ehjäksi. Kaikilla kentillä on oletus, joten bean sitoutuu joka profiilissa; **puutteellinen kartoitus kaataa `tuo()`:n ennen atarun kutsua** (`puutteet()`), koska muuten jokainen hakemus päätyisi virheeksi. Hyväksymisehdot (`ArvioijahakemusKriteeri.atarunTilat`: atarussa käsitelty + hakukelpoinen, ei passivoitu) ovat koodissa, koska atarun tilojen nimet ovat kaikkialla samat — ja ne **ajetaan atarussa**, koska kirjattua hakemusta ei haeta uudelleen: kituun kirjattu muuttuva ehto ei koskaan kääntyisi. Muut asetukset: `kitu.ataru.service.url` (tyhjä = koko integraatio pois, palvelua ja eräajoa ei synny) ja `kitu.ataru.arvioijahakemus.schedule`. Tila elää taulussa `yki_arvioijahakemus` (V130): rivi = hakemus käsitelty eikä sitä haeta uudelleen — **paitsi `ODOTTAA_YKSILOINTIA`** (henkilöä ei ole vielä yksilöity ONR:ssä; henkilöttömän hakemuksen siirto jättää kokonaan pois), joka haetaan joka ajolla uudelleen kunnes se ratkeaa. Ennen `luoArvioija`a rivi kirjataan tilaan `KASITTELYSSA` ja viimeistellään sen jälkeen, joten kaatuminen niiden välissä jättää rivin näkyviin eikä luo seuraavalla ajolla toista kautta; yksittäisen hakemuksen poikkeus ei pysäytä muita, vaan ajo heittää vasta lopuksi. **Pysyvää hylkäystä ei ole** (V135 poisti `HYLATTY`n ja `EI_TAYTA_EHTOJA`n): jokainen ei-ohimenevä epäonnistuminen — siirron rakennevirhe, kartoitusvirhe, ONR ei tunne henkilöä, osoite puuttuu sekä hakemukselta että ONR:stä, `luoArvioija`n validointivirhe — kirjataan tauluun `yki_arvioijahakemus_virhe` (näkymä `/yki/arvioijat/hakemukset/virheet` + etusivun rivi) **ilman kirjanpitoriviä**, joten hakemus haetaan joka ajolla uudelleen ja käsitellään, kun syy (esim. kartoitus) on korjattu; kirjatut virheet eivät kaada ajoa. Virherivi ja kirjanpitorivi eivät ole yhtä aikaa olemassa: virheen kirjaus poistaa `ODOTTAA_YKSILOINTIA`-rivin, lopullinen kirjaus poistaa virherivin ensin, ja ajon alussa `poistaKirjatut` siivoaa `KASITTELYSSA`-kaatumisen jäljet. Virherivit poistuvat myös, kun hakemus ei enää ole atarun listauksessa — **paitsi tyhjällä listauksella**, koska puuttuva oikeus näkyy tyhjänä vastauksena. **`luoArvioija` palauttaa ennen tallennusta vain `Validointivirheet`in ja `MuokattuSamanaikaisesti`n**; muu Left (esim. `lahetaSolkiin`in `ArvioijaaEiLoydy`) tulee tallennuksen jälkeen, joten se jättää rivin tilaan `KASITTELYSSA` ja kaataa ajon — uusi yritys loisi toisen kauden. Taulu `yki_arvioijahakemus` on **pelkkä kirjanpito ilman säilytysaikaa** — älä lisää sille vartioimatonta poistoa, sillä poistettu `KASITELTY`-rivi saisi seuraavan ajon luomaan arvioijan uudelleen; ainoa poisto on tilalla vartioitu `poista(oid, tila)`. **Ohimenevät virheet (ONR ei vastaa, samanaikainen muokkaus) jätetään tarkoituksella kirjaamatta.** Virheisiin talletetaan kartoitetun vastauksen arvo, mutta siirron rakennevirheestä vain JSON-polku: **Jacksonin virheviesti voi toistaa syötteen arvon (myös hetun)**, joten sitä ei talleteta eikä lokiteta, ja `ArvioijahakemuksenVirhe.tallennettava` on viimeinen suoja (hetu-regex, `ssn`/`birth-date`, 500 merkkiä). Siirto jäsennetään alkio kerrallaan (`SiirtoHakemus.jasenna`), jottei yksi rikkinäinen hakemus kaada koko erää, ja yhteystieto luetaan vain `isString`-solmusta, koska Jackson 3:n `asString()` heittää taulukolle ja objektille. Ansat: (1) ataru hyväksyy **vain CAS:n**, ei OAuth2:ta — `security/cas/client/CasSessionClient` on kitun ainoa lähtevä CAS-asiakas (TGT → ST → `ring-session`-eväste, 401 → uudelleenkirjautuminen); (2) `koto-rekisteri` saa `ATARU_HAKEMUS` READ -oikeuden lomakkeen omistavaan OPH:n **alaorganisaatioon** (ei juureen, joka tekisi siitä ataru-superuserin), ja puuttuva oikeus näkyy **tyhjänä vastauksena, ei virheenä**; (3) listaus käyttää atarun virkailija-UI:n reittiä `/api/applications/list`, joka ei ole sovittu ulkoinen rajapinta — ja vaatii `states-and-filters`-kentän (`StatesAndFilters`), vaikka skeema sallii sen puuttumisen: ilman sitä ataru kaatuu 500:aan, ja puuttuva tilalista pudottaa hiljaa kaikki hakemukset. `MockAtaruClient` ei paljasta tätä, joten e2e ei auta; (3b) **siirron `keyValues` on litistetty eikä sisällä koskaan taulukoita**: monivalinnan valittu vaihtoehto on avain `<kentän id>_<vaihtoehdon arvo>`, ja itse kirjoitettujen vaihtoehtojen arvot ovat järjestysnumeroita `"0"`, `"1"`, … — siksi kitu muodostaa vastausavaimen kysymyksen id:stä ja vaihtoehdon arvosta, ja tuntematon vaihtoehto (myös `_group`-avain) kartoitetussa kysymyksessä kirjaa hakemuksen virheeksi. Siirto myös jättää hiljaa pois henkilöttömät ja (ilman `returnInactivated=true`:ta) passivoidut hakemukset, joten kitu ei tarkista niitä itse ja `SiirtoHakemus.personOid` on ei-nullable; (4) lomakkeen vuoden raja kauden alkupäivälle (`validateKaudenAlkupaiva`) **ohitetaan** automaattiselle jatkokaudelle `TallennaArvioija.automaattinenJatkokausi`-lipulla, koska jatkokausi alkaa vasta voimassa olevan kauden päätyttyä — lippu ei ole vapaa ohitus, vaan `TallennaArvioijaValidation` vaatii silloin, että jokin olemassa oleva kausi päättyy alkupäivää edeltävänä päivänä. e2e/`local-opintopolku` käyttää `MockAtaruClient`ia (fixture `opintopolku-mocks/ataru/`).
- `kotoutumiskoulutus/` — integrates with the Koealusta kielitesti service. **Valmiit ovat inkrementaalisia, keskeneräiset täysi korvaus:** `importValmiitSuoritukset` saa `from`-vesileiman db-schedulerilta (`recurringStatefulTask<Instant>`) ja tallentaa vain uudet, kun taas `importKeskeneraisetSuoritukset` tekee joka ajolla `deleteAllKeskeneraiset()` + `saveAll`. Keskeneräisten haku rajataan Moodlen `enrolledfrom`-parametrilla (`timeService.now()` miinus `kitu.kotoutumiskoulutus.koealusta.keskeneraiset.enrolmentWindow`, oletus `14d`, `kotlin.time.Duration`; **tyhjä arvo jättää parametrin pois**, mikä on se tapa perua rajaus jos Mediamaisterin pää ei vielä tunne parametria). **Siksi ikkuna on samalla säilytysaika**: ikkunasta valunut keskeneräinen katoaa seuraavassa ajossa, eikä tälle ole saraketta tai migraatiota. **Kaikki Moodle-aikaleimat ovat epoch-sekunteja** molempiin suuntiin (`.epochSecond` / `Instant.ofEpochSecond`) — laske ikkuna `timeService.now()`:sta, älä `today()`:stä, muuten palaa Europe/Helsinki-vs-UTC-ansa. Keskeneräisten kartoitus nojaa siihen, että `KoealustaMappingService` on tarkistanut `isOnrValidateable()`-ehdon ennen `courseToEntity`-kutsua; validaattori ei tarkista `preferredname`a enää uudelleen, eikä `courseToEntity` siksi enää palauta nullia. Molemmat koealusta-ajot jakavat yhden `...koealusta.scheduling.import.schedule`-arvon. **Tuontivirheet päivitetään, ei korvata** (`KielitestiErrorService.syncErrors`): virhe on sama, jos `(completed, hetu, viesti)` täsmää, jolloin se säilyttää id:nsä ja `virheen_luontiaika`nsa ja muut kentät päivittyvät paikallaan; `lisatietoja` ei kuulu tunnisteeseen, koska ONR:n virhevastaus kantaa omaa aikaleimaansa. Myöskään virheen kurssitiedot (`kurssi_id`, `kurssi`, `suoritusaika`, V137) eivät kuulu siihen: henkilötason virheet (ONR, puuttuva SSN/preferredname) ottavat ne henkilön ensimmäiseltä suoritukselta samoin kuin `school_oid`:n ja `teacher_email`:n, ja niiden lisääminen tunnisteeseen nollaisi jokaisen ennen V137:ää kirjatun virheen luontiajan. **Valmiiden vesileima:** virheettömässä ajossa uusin `timecompleted`; jos ajossa on virheitä, sekunti ennen **varhaisinta epäonnistunutta suoritusta** (`ValidationFailure.varhaisinEpaonnistunutSuoritus`: ONR- tai henkilövalidointivirheessä tietueen kaikki suoritukset, suoritusvirheessä vain se suoritus; ohitettu virhe ei laske), mutta ei koskaan taaksepäin. Sekunti on varmuusvara, koska koealustan `from`-rajan avoimuutta ei tunneta. Epäonnistunut suoritus **pitää** pysyä hakuikkunassa, koska virheet synkronoidaan "mitä tämä ajo näki" -periaatteella: ikkunan ulkopuolelle jäänyt virhe poistuisi korjaantumatta. Ennen tätä vesileima pysähtyi koko virheiden ajaksi ensimmäiseen virheelliseen ajoon. Korjaamaton virhe pitää yhä ikkunan auki omasta suoritusajastaan alkaen, ja sama virhe löytyy joka ajolla uudelleen — **siksi henkilötietovirheille (`onr_status` 400/404/409, `HENKILOTIETOVIRHEEN_TILAT`) ei ajeta nimiyhdistelmien vianetsintää uudelleen** (se tekisi kymmeniä ONR-kutsuja per henkilö per ajo): jokainen ajo tekee silti yhden oppijanumeron haun, ja jos ONR vastaa samalla tilalla ja virheviestillä kuin kirjattu virhe ja hetu ja nimet koealustalla ovat ennallaan, kirjattu virhe ratkaisuehdotuksineen toistetaan sellaisenaan. **Älä jätä tuota yhtä hakua pois**: 26.–28.10.2026 välimuisti ohitti senkin, jolloin ONR:n päässä korjattu virhe jäi virhenäkymään, kunnes koealustan tiedot muuttuivat. Onnistunut haku poistaa virheen; muuttunut tila tai viesti, ONR-katkokset, 401/403 ja yksilöimättömät (`onr_status` NULL tai muu) ajavat vianetsinnän joka kerta. **Jo tallennetusta suorituksesta ei kirjata ONR-virhettä:** varhaisimman virheen jälkeen tuodut suoritukset tarkistetaan joka yö uudelleen, joten myöhempi Moodle-profiilin muutos tai saman suorituksen toinen tietue kirjaisi virheen suoritukselle, joka on jo kitussa. Kun ONR hylkää tietueen, `suorituksetOnTallennettuHetulle` katsoo **ennen vianetsintää**, onko tietueen jokainen suoritus (`kurssi_id` + `suoritusaika`) jo tallennettu sille oppijanumerolle, jonka ONR antaa hetulla (`henkilo/hetu=`); jos on, virhettä ei kirjata. Tietokantahaku tehdään ensin, joten hetuhaku tehdään vain kun jokaiselle suoritukselle löytyy tallennettu ehdokas. **Testiansa:** `KoealustaServiceTests` jakaa yhden kontekstin ja yhden `MockRestServiceServer`in kaikkien testiensä kesken (`PER_CLASS` + `reset()` `@BeforeEach`issä). Inline-`properties` antaa luokalle oman kontekstiavaimen, joten `KoealustaService`n laiska `RestClient` ei ole ehtinyt rakentua ennen sidontaa, ja `AFTER_CLASS` sulkee kontekstin ettei mock vuoda muihin luokkiin. **Älä palauta `BEFORE_EACH_TEST_METHOD`ia**: se rakensi kontekstin 24 kertaa ja vei ~6 min CI:n ~8 min testiajasta. Samasta syystä testit eivät saa olettaa id-sekvenssin alkavan ykkösestä, ja testin muuttamat palvelun kentät (`keskeneraisetEnrolmentWindow`) palautetaan `@BeforeEach`issä.
- **YKI-historian karanteenitaulu** `yki_historia_siirtymaton` (V127): YKI-historiamigraatioissa siirtymättä jääneet lähderivit sellaisenaan + syy. **Taululla ei ole sovelluskoodia** — data luetaan tarvittaessa SQL:llä, ja rivit ladataan CloudShellista **RDS Data API:n** kautta. Karanteenissa olevasta rivistä ei lähde mitään KOSKI-järjestelmään, ONR:ään tai ilmoittautumisjärjestelmään, eikä sitä lasketa suoritukseksi. **Kaikki lähdesarakkeet ovat TEXT ja talletetaan sellaisenaan**, koska juuri näissä riveissä ovat ne arvot joita ei voitu jäsentää (katkaistut hetut, jäsentymättömät aikaleimat, väärät sarakemäärät) — tyypitys hylkäisi juuri sen datan joka on tarkoitus saada talteen. **Karanteenista rekisteriin siirretään SQL-migraatioilla**: V129 (2011–2016) siirtää muunnettavissa olevat ja kirjoittaa jäljelle jäävien `syy`/`syyluokka`n uudelleen; **V132** (jälkisiirto 2016–2020) ja **V133** (Solkin 2021–3/2026-viennistä puuttuneet) ovat sen kopioita, jotka siirtävät **vain oppijanumerottomat** — rajapinnan hylkäämä oppijanumerollinen rivi ei saa ohittaa validointia ja ONR-kartoitusta SQL:n kautta, joten uusi vastaava migraatio noudattaa samaa rajausta ja toistaa rajapinnan säännöt SQL:nä. Siirtojen vaiheet, määrät ja skriptit (`scripts/migrate_yki_historia.py`, `load_yki_historia_siirtymattomat.py`, `yki_jalkisiirto.sh`, `yki_puuttuvat_suoritukset.py`, `yki_puuttuvien_siirto.sh`, `duckdb_session.sh`) ovat runbookissa `scripts/yki-historia-migration.md`; skriptit **palautettiin 14.10.2026** määrien täsmäytystä varten, ja runbookin alussa on lueteltu mikä niistä ei enää toimi. Vuoden 2026 riveiltä hetu pudotetaan jo skripteissä. S3-latauksen presign-apuri (`scripts/yki_historia_upload_presign.sh` → `infra/scripts/presign-yki-historia-upload.mjs`) toimii **ilman CDK-pinoa**, koska ämpäri `kitu-yki-historia-upload-prod` on `RETAIN`in vuoksi yhä olemassa. Apurin S3-client tarvitsee `requestChecksumCalculation: "WHEN_REQUIRED"`: SDK:n oletus allekirjoittaa PUT-osoitteeseen tyhjän rungon CRC32:n, ja S3 hylkää silloin oikean tiedoston. LocalStack ei tarkista tätä, joten paikallinen kokeilu ei paljasta vikaa.
- **YKI-suoritus ilman oppijanumeroa — sallittu kannassa, estetty kaikkialla muualla:** `yki_suoritus.suorittajan_oid` on **nullable V128:sta alkaen** ja `YkiSuoritusEntity.suorittajanOID` on `Oid?`. NULL on **vain karanteenitaulun kautta SQL-migraatiolla siirrettyjen rivien erikoistapaus**: V129 (2011–2016), V132 (jälkisiirto 2016–2020) ja V133 (Solkin 2021–3/2026-viennistä puuttuneet, jotka eivät koskaan tulleet kituun) — rivit, joille oppijanumeroa ei ole. Kolme asiaa pitävät sen erikoistapauksena: (1) **rajapinta ei päästä sellaista läpi** — `tiedontuontischema/Henkilo.oid` on ei-nullable ilman default-arvoa, joten Jackson kaatuu ja `GlobalControllerExceptionHandler` tekee siitä 400:n; erillistä validaattoria **ei ole eikä pidä lisätä**, ja `Henkilo` on yhteinen VKT:n kanssa joten kentän nullableksi tekeminen levittäisi muutoksen sinne turhaan (`YkiApiControllerTest` kiinnittää 400:n). (2) **KOSKI-siirto on estetty kahdessa kerroksessa**: `KoskiYkiRequestMapper.koskiSiirronEstonSyyt` lisää syyn "Suorituksella ei ole oppijanumeroa" (tämä on arvovaltainen portti ja näkyy tietosivulla sekä `/yki/koski-request/{id}`-reitillä), **ja** `findKoskeenLahettamattomatSuoritukset` suodattaa `suorittajan_oid IS NOT NULL`. Pelkkä mapperin esto ei riitä, koska `KoskiService` kirjoittaa `EstoSyyt`-haarassa `koskiSiirtoKasitelty = true` — rivi leimautuisi käsitellyksi eikä siirtyisi koskaan, vaikka oppijanumero myöhemmin saataisiin. (3) **Ilmoittautumisjärjestelmä samoin**: `YkiSuorituksenTunniste.of` palauttaa **nullin** ilman oppijanumeroa (ja `YkiArvioinninTila.of` sen myötä, samaan tapaan kuin `isVilppi()`-riveillä), ja `findSuorituksetWithUnsentArvioinninTila` suodattaa samalla ehdolla — ilman SQL-suodatinta rivi luettaisiin joka ajolla uudelleen, koska nulliksi mäppäytyvää ei koskaan merkitä lähetetyksi. Tietosivu **ohittaa ONR-haun** kun oppijanumeroa ei ole (`YkiViewController` kutsuu `getHenkiloByHenkiloOid`ia vain `?.let`-haarassa, ja `YkiSuoritusPage.render`in `henkilo` on nullable = "ONR:ää ei kysytty"), eikä tarjoa yksilöintilinkkiä joka johtaisi 404:ään.
- **SQL-migraatio joka kaytaa jasentymatonta dataa: `pg_input_is_valid`, ei casteja.** Flyway ajaa migraation yhdessä transaktiossa, joten **yksikin kaatuva cast kaataa koko migraation** — eikä `to_date` pelasta: `to_date('2011-02-30','YYYY-MM-DD')` kaatuu (se **ei** rullaa yli), kuten myös `make_date`, eikä `CAST(x AS date DEFAULT NULL ON ERROR)` ole tuettu. `pg_input_is_valid(teksti, tyyppi)` on totaali ja tuntee myös **domainit ja enumit**, joten esim. `iso_oid`-domainin regexp-CHECKiä ei tarvitse kirjoittaa uudelleen. **Vaatii Postgres 16+** (tuotanto on Aurora PostgreSQL 16.4, `infra/lib/db-stack.ts`). **Ansa:** `pg_input_is_valid(NULL, …)` on **NULL** eikä NULL ole tosi, joten paljas kutsu WHERE-lauseessa pudottaa hiljaa NULL-rivit — pakolliselle kentälle `col IS NOT NULL AND pg_input_is_valid(...)`, valinnaiselle `col IS NULL OR pg_input_is_valid(...)`. Enum-tarkistus on kirjainkoon suhteen tarkka (`fin` ei kelpaa, `FIN` kelpaa). Älä myöskään nojaa `AND`:in oikosulkuun castin suojana — Postgres ei takaa evaluointijärjestystä, joten käytä `CASE`ia tai `MATERIALIZED`-aitaa. Kuivaharjoittele predikaatti read-only-SELECTinä ennen ajoa. **Väliaikaistaulut: älä käytä `ON COMMIT DROP`**, vaan `DROP TABLE IF EXISTS` ennen luontia ja lopussa. Flyway ajaa migraation yhdessä transaktiossa, mutta `psql -f` ajaa **jokaisen lauseen omana transaktionaan**, jolloin `ON COMMIT DROP` tuhoaa taulun heti ensimmäisen lauseen jälkeen ja seuraava lause kaatuu `relation ... does not exist` -virheeseen — eli migraatiota ei voisi kuivaharjoitella eikä ajaa käsin lainkaan, mikä on juuri se mitä tuotannon datamigraatiolle halutaan tehdä. Huom myös ettei tämä näy Testcontainers-testissä, jos testi antaa koko tiedoston yhtenä `jdbc.execute`-kutsuna (Postgres ajaa monilauseisen kyselyn yhtenä implisiittisenä transaktiona).

### Cross-cutting pieces worth knowing

- **DB & migrations**: Spring JDBC (no JPA entity manager) over Flyway. Migrations in `server/src/main/resources/db/migration` (`V*__*.sql`). Schema docs are generated by `docs/build.sh` via SchemaSpy. The V-numbering has gaps (V7, V38, V46–V55, V65, V104, V105) left over from repaired out-of-order deploys (V65 → V67, V104/V105 → V108/V109). Don't reuse skipped numbers; continue past the highest (`ls server/src/main/resources/db/migration | sort -V | tail -1`). **Index decisions need Postgres 16, not the local container:** `possu.Dockerfile` is Postgres **18**, prod is Aurora **16.4**, and PG18's B-tree skip scan serves a composite index's non-leading column (e.g. `(taitotaso, ilmoittautumisen_id)` for `WHERE ilmoittautumisen_id = ?`), so local `EXPLAIN` hides indexes that are missing in prod. Benchmark on a `postgres:16` image with the same `localedef … fi_FI` line (the schema needs that collation), restored from a full `pg_dump`. **`YkiSuoritusSql.selectSuorituksetFull` can't use filter-column indexes:** it appends the caller's `WHERE` after the `DISTINCT ON (solki_id)` CTE, and only `solki_id` predicates are pushed into it (`id = ?` works via the join equivalence) — an index on any other filtered column is dead weight there.
- **Aika ja "tämä päivä" testeissä**: sovelluksen käsitys tästä päivästä on **aina `Europe/Helsinki`** — `TimeService.zoneId` kovakoodaa sen ja `TimeService.today()` johtaa päivän siitä. CI-ajurit ovat **UTC**:ssa, joten testi joka laskee oman "tämän päivänsä" `LocalDate.now()`:lla (JVM:n oletusvyöhyke) tai JS:n `new Date()`:lla on eri päivässä kuin palvelin klo **21–24 UTC** välillä, ja jokainen päivärajaan nojaava väite kääntyy. Oire: yöaikaan kaatuva testi, joka menee aamulla uusinta-ajolla läpi — näyttää "flakyltä" vaikka on täysin deterministinen. **Server-testit:** injektoi `TestTimeService` (profiili `test`) ja kiinnitä hetki `runWithFixedClock(...)`:lla, ja johda odotetut päivät `timeService.today()`:stä — älä käytä `LocalDate.now()`:ta. **E2E:** `playwright.config.ts` asettaa `process.env.TZ = "Europe/Helsinki"` (ja selaimen `timezoneId`) koko ajolle, jotta spekin `new Date()` vastaa palvelinta — älä poista sitä. Huom: kaikki testin `LocalDate.now()` ei ole vika — se on vika vain jos arvoa verrataan palvelimen laskemaan päivään (esim. `Rekisterointitila.laske` oikosulkee tallennettuun `PASSIVOITU`-tilaan, jolloin päiväargumentti on merkityksetön).
- **Scheduled work**: uses `db-scheduler` (kagkarlsson). Tasks are enabled/disabled per Spring profile via properties (`kitu.yki.scheduling.*`, `kitu.vkt.scheduling.*`, etc.). There's a db-scheduler UI mounted by the app; see `docs/db-scheduler/README.md`. The `db-scheduler-log` add-on is **vendored** at `server/src/main/kotlin/io/rocketbase/extension/` (port of 0.7.0 with SB4 package relocations) until an upstream SB4-compatible release exists — see the package README for the rollback procedure. Schedule strings go through `ExtendedSchedules.parse` (`util/scheduling/`): it accepts the built-in forms (`FIXED_DELAY|Ns`, `DAILY|HH:mm`, `-`) and falls back to **SPRID53 cron** (6 fields `sec min hour dom month dow`, `?` allowed, **no year field** — Quartz-style 7-field crons fail). **Gotcha for "manual"/on-demand tasks:** a `-` (disabled) schedule does **not** make a task that's triggerable from the UI — db-scheduler deliberately never creates a `scheduled_tasks` row for a disabled recurring task (and removes any existing one) in `ScheduleRecurringOnStartup`, and the UI lists only existing executions, so the task is invisible with no "Run now". To get a UI-triggerable-but-effectively-never-auto-running task, give it a rare real cron (e.g. `0 0 0 29 2 ?` = leap-year Feb 29) rather than `-`.
- **JSON**: Jackson 3 (`tools.jackson.*` packages, e.g. `tools.jackson.databind.json.JsonMapper`). Annotations still come from `com.fasterxml.jackson.annotation` (kept for backward compat). `JavaTimeModule` no longer exists — register `java.time` serializers via `SimpleModule()`. `ObjectMapper.copy()` is gone — use `.rebuild()...build()`. Accessor renames on `JsonNode`/`JsonParser`: `textValue()` → `stringValue()`, `asText()` → `asString()`, `p.text` → `p.string`. Custom deserializers should extend `ValueDeserializer<Any>` for `@JsonDeserialize(using = ...)` compatibility.
- **JSON-pyyntöjen rungot validoidaan tiukasti UTF-8:ksi (OPHKOTO-91)**: Spring antaa UTF-8-rungon Jacksonille tavuvirtana, ja `UTF8StreamJsonParser` hyväksyy **ylipitkät koodaukset** (`C0 BC` = `<`, `C0 80` = NUL) tarkistamatta. Siksi `webmvc/MessageConverterConfig` vaihtaa palvelimen konvertterilistan **jokaisen** `JacksonJsonHttpMessageConverter`in `StrictUtf8JsonHttpMessageConverter`iksi (sama mapper ja mediatyypit): se lukee rungon `Utf8ValidatingInputStream`in läpi (JDK:n tiukka dekooderi) ja hylkää merkkijonojen NUL-merkit, jotka Postgres hylkää `text`-sarakkeessa ja jotka siksi kaatuivat 500:aan. Molemmat päätyvät olemassa olevaan `HttpMessageNotReadableException` → 400 -polkuun. Vaihto tehdään listassa eikä `withJsonConverter`illa, koska `yhteystiedot/YhteystiedotApiJacksonConfig`in konvertteribean rekisteröityy custom-konvertteriksi listan alkuun — **kaikki MVC:n JSON-rungot luetaan siis `koskiObjectMapper`illa**. Strict-konvertterista ei saa tehdä beania: Boot antaa jokaisen `HttpMessageConverter`-beanin myös asiakaspuolen (RestClient) konverttereille. Lomakkeet ja URL:t dekoodaa Tomcat, ei tämä polku: Tomcat hylkää ylipitkän UTF-8:n niissä itse (400), ja NUL-merkin hylkää `webmvc/NulRejectingBindingAdvice` — globaali `@InitBinder`, joka rekisteröi `String`-editorin, joten se koskee `@ModelAttribute`-lomakkeita, `@RequestParam`eja ja polkumuuttujia. Sidontavirhe on `BindException` (lomake) tai `MethodArgumentTypeMismatchException` (parametri), ja `GlobalControllerExceptionHandler` näyttää molemmista 400-sivun — ennen tätä `BindException` päätyi 500-sivulle, koska yksikään virkailijanäkymä ei ota `BindingResult`ia.

- **Auth / CAS single logout**: browser auth is CAS (Otuva) — `CasAuthenticationFilter` is wired in `security/cas/CasConfig.kt`, `SingleSignOutFilter` one package up in `security/WebSecurityConfig.kt`. Otuva does **back-channel** single logout: on `/cas/logout` (e.g. from the virkailija-raamit menu) CAS POSTs a `logoutRequest` to the service URL and the service must invalidate **its own** session — CAS never clears the browser `SESSION` cookie. Because kitu uses **Spring Session JDBC**, the apereo filter's default in-memory `SessionMappingStorage` can't find/invalidate the DB session (and breaks across instances), so it's wired via the **static** `SingleSignOutFilter.setSessionMappingStorage(...)` to a DB-backed `JdbcSessionMappingStorage` (service-ticket→Spring-Session-id in table `cas_client_session`; `session_id` is deliberately **not** UNIQUE — one browser session can hold several tickets, OPH KJHH-2045). Don't push injected deps into an abstract base (`@WithSpan` CGLIB trap) and don't add a session-fixation strategy to the manual `CasAuthenticationFilter` — it sets none, so it keeps `AbstractAuthenticationProcessingFilter`'s no-op default and the session id stays stable, which is what keeps the login-time ST→session mapping valid. **The logout POST carries no cookie and no CSRF token**, so `/j_spring_cas_security_check` must stay in the CAS chain's CSRF `ignoringRequestMatchers`: `CsrfFilter` sits before `SingleSignOutFilter` in the chain and otherwise answers 403. That is how SLO stayed broken from 7/2026 to 10/2026 even though the storage was correct (untuva spans: every CAS POST → 403). The `e2e` profile disables CSRF, so e2e cannot catch a regression; `CasSingleLogoutTest` drives login → logout POST → stale cookie through the real filter chain with Spring Session JDBC. In MockMvc, put the ticket **in the URL** (`?ticket=ST-1`), not `.param(...)`: apereo's `safeGetParameter` reads `ticket` only when it appears in `getQueryString()`. Consequence: `CasUserDetails` attributes (incl. `asiointikieli`, see i18n) are a **login-time snapshot** and only refresh on a real re-login.

Kopioinnin hoitaa yksi delegoitu kuuntelija, jonka `Page.renderHtml` lisää jokaiselle sivulle (`copyButtonScript`), joten painike toimii myös listoissa ja jälkikäteen ladatussa sisällössä. Kaksi rajoitetta: painikkeen merkintä on **pelkkä arvon funktio** (ei satunnaisia id:itä), koska `comparisonTable` päättelee `diff`-korostuksen vertaamalla solujen HTML:ää; ja siinä **ei ole tekstisisältöä** (SVG + `aria-label`), jotta solun teksti ja e2e:n `toHaveText(oid)` pysyvät ennallaan. `aria-label` päätyy silti solun saavutettavaan nimeen, joten `getByRole("cell", { name, exact: true })` ei täsmää tällaiseen soluun.

URL:t ovat **käännösavaimia** (`ohje.*` `UiText.Ohje`ssa + `lokalisointi/fi.json`), jotta OPH:n virkailija voi vaihtaa ne Tolgeessa ilman deployta, ja kieliversion wikisivu on pelkkä sv/en-käännös. `html/Ohje.kt`:n `ohjeUrl` käyttää sivukohtaista arvoa vain jos se alkaa `http(s)://`; tyhjä, puuttuva (joka muuten renderöityisi raakana avaimena) tai virheellinen arvo palaa `ohje.oletus`een. Siksi sivukohtainen avain jolla ei ole omaa sivua on fi.json:ssa **tyhjä merkkijono** — ja `TolgeeClientImpl.createKeys` luo tyhjän lähdetekstin avaimen ilman fi-käännöstä. Uusi näkymä: lisää `ohje.<alue>.<sivu>`-avain molempiin ja välitä se `renderHtml`ille; ilman parametria sivu saa oletusohjeen.
- **Virhesivut HTML-näkymissä**: a virkailija view signals "ei löydy" by **throwing** a subclass of `webmvc/ResourceNotFoundException` — one per domain, declared at the bottom of the owning `*ViewController.kt` (`VktSuoritusNotFoundError`, `YkiSuoritusNotFoundError`, `YkiArvioijaNotFoundError`, `ArvioijahakemusNotFoundError`, `KielitestiSuoritusNotFoundError`, `TehtavapankkiNotFoundError`) — and **never** by returning `ResponseEntity.notFound().build()`, which sends a bodiless 404 and shows the virkailija a blank page. `GlobalControllerExceptionHandler.handleServerException` matches the **base type**, so a new domain needs no change there; the `@ExceptionHandler(Throwable)` advice wins over Spring's own `@ResponseStatus` resolution, so an exception outside that hierarchy would drop into the `else` branch and render the **500** page instead of 404. The base class carries `@ResponseStatus`, and the `reason` goes to the exception message; neither reaches the user (the handler renders `ErrorPage.notFound`, i.e. `UiText.Error.sivuaEiLoydy`), so it only documents intent in logs/traces. `ResponseEntity<Void>` endpoints (e.g. tehtäväpankin `/lataa`-uudelleenohjaus) throw the same way — the advice produces `text/html` regardless of the handler's declared return type. Machine-readable endpoints (`produces = ["application/json"]`, e.g. the `koski-request` debug routes) **deliberately keep** the bodiless 404; don't "fix" those. `EiLoydyVirhesivuTest` pins the HTML routes and guards the JSON exception.
- **Display tables & CSV export (`html/table/*`)**: a list view and its CSV download share one column source — an enum implementing `RenderableDisplayTableEnum<T>` (e.g. `YkiSuoritusColumn`, `VktSuoritusColumn`), where each entry supplies `entityName`, `uiHeaderValue: LocalizedString`, `urlParam`, a `getValue: (T) -> String` (the CSV/text cell) and an optional `renderHtml` (overrides the HTML cell). **Which columns appear in HTML vs CSV is decided purely by `@ColumnTags(...)`, and the two are independent include-tags**: the HTML table selects `LIST_VIEW` (`DisplayTableColumn.of<C,T>(setOf(ColumnTag.LIST_VIEW), excludeTags)` in the `*Page`), while the CSV export selects `CSV_EXPORT` — **hard-coded** inside `DisplayTableCsvRenderer.renderCsv` (via `csvAttachmentResponse<C,_>`). So to add a column to the **CSV only**, annotate it `@ColumnTags(ColumnTag.CSV_EXPORT)` **without** `LIST_VIEW` (and vice-versa; a column can carry both, one, or neither). The filter itself is `RenderableDisplayTableEnum.getByTags` (`html/table/DisplayTableEnum.kt`): keep iff the entry's tag set intersects `require` **and** does not intersect `exclude`. The remaining `ColumnTag`s are request-driven **exclude** toggles applied to both paths, computed by `*SuorituksetParams.excludeTags()`: `PERSONAL_DATA` (dropped when "piilota henkilötiedot"), `OBSOLETE` ("piilota vanhentuneet tiedot"), `VERSION_HISTORY_ONLY` (kept only in the version-history view). CSV column **order = enum declaration order**; headers come from `uiHeaderValue` and follow the UI language (see i18n gotcha #2). All rows are read from the already-materialized entity `T`, so a new column that only reads existing entity fields needs no DB/SQL/service change — just the enum entry (+ a `UiText` header label). **CSV columns are a contract with the virkailijat's spreadsheets: never rename or remove a CSV column without asking, and add new `CSV_EXPORT` entries after the existing ones** so the order of existing columns never moves.
- **List-view filters are multi-select (`html/table/TableFilterDialog.kt`)**: `enumFilter` renders a Pico `details.dropdown` of checkboxes (`html/MultiSelectDropdown.kt`). **Nothing checked means no filtering on that field**, values within one field are OR'ed (SQL via `jdbc/SqlFilter.kt`'s `addAnyOf` = `col IN (:param)`, which relies on `stringtype=unspecified` for enum columns; arvioijan `taso` is an array overlap `&&`), and fields stay AND'ed. The `*Params`/`*Filter` field is therefore `List<E> = emptyList()`, never `E?`. A list reaches the server two ways that both bind to `List<E>`: the dialog form sends repeated params (`?kieli=FIN&kieli=SWE`), while `toMap()` (sort/pagination/CSV/tilastot links and `hiddenValues`) sends them comma-joined via `toUrlParam()` (`?kieli=FIN,SWE`) — so `httpParams` stays single-valued. `valintaDescription` and `toCsvFilenameSegment` render the filter description and the CSV filename part; one selected value gives exactly the old single-value output. Pico closes the dropdown on an outside click by itself (an open dropdown's `summary::before` is a fixed full-viewport overlay); the only JS is the per-dropdown summary-text update and scrolling an opened list into view. The list deliberately stays inside the dialog's own scroll area (Pico's `dialog > article` is `overflow: auto`): **don't make the article `overflow: visible`** — the dialog itself can't scroll, so on a short viewport (≈ laptop height) the bottom dropdown's options would end up off-screen and unreachable. Inside a dialog, `style.css` also sizes that overlay with `inset: 0` instead of Pico's `100vw × 100vh`: the dialog's `backdrop-filter` makes it the overlay's containing block and a modal `<dialog>` is `overflow: auto`, so `100vw` (which includes the page scrollbar) gave the dialog scrollbars and shifted the centred modal up-left by half a scrollbar on open. Playwright launches Chromium with `--hide-scrollbars`, so this is invisible in e2e and screenshots — reproduce with `ignoreDefaultArgs: ["--hide-scrollbars"]`. `enumRadioFilter` is for **mutually exclusive modes** only (koto `NaytettavatSuoritukset`), not for filters.
- **Localization (i18n)**: FI/SV/EN. `LocalizedString(fi, sv, en)` (`i18n/LocalizedString.kt`) is the multilingual primitive for **both** koodisto reference data (loaded fi/sv/en from the koodisto service via `Translations`/`LocalizationService`) and static UI chrome. UI chrome lives in the typed catalog `i18n/UiText.kt`, where each entry is `tr("dotted.key")` — a computed getter (or a function that `.interpolate("count" to n)`s a `{count}` placeholder for parameterized strings). **`UiText.kt` holds only keys: there is no Finnish text in Kotlin.** The Finnish source text lives in the checked-in resource `server/src/main/resources/lokalisointi/fi.json` (with `sv.json`/`en.json` alongside it), which is loaded from the classpath in **every** profile. All three languages are additionally resolved at runtime from **Tolgee** via OPH's lokalisointi proxy (see "Tolgee sourcing" below), and the live value wins **per language** over the checked-in one. **No** Spring `MessageSource`/`messages*.properties` — do not add them. `LocalizedString.get(lang)` returns the requested language, **falling back to `fi`** (then, for a catalog string, the **key itself**; then the literal `"<invalid LocalizedString>"`) when that language is missing — so a half-migrated page renders untranslated bits in Finnish rather than blank; this is what makes package-by-package migration safe. `toString()` resolves the **ambient** `CurrentLanguage` (it is defined as `get(CurrentLanguage.get())`), so plain string interpolation and `+` emit the current UI language. The active language is resolved **ambiently**, not threaded: a `CookieLocaleResolver("kitu_lang")` + `LocaleChangeInterceptor(paramName="lang")` (`i18n/LocalizationConfig.kt`, bean **must** be named `localeResolver`) sets Spring's `LocaleContextHolder`, and `CurrentLanguage.get()` (`i18n/CurrentLanguage.kt`, a plain `object` — **not** a `@Service`, to avoid the `@WithSpan` CGLIB trap) reads it, defaulting to FI when no request is bound. Renderers emit a translated string by writing `+someLocalizedString` directly inside a tag block (e.g. `strong { +it.title }`), via the sole helper in `i18n/HtmlLocalization.kt`: `operator fun LocalizedString.unaryPlus()`. It's a `context(tag: Tag)` function — this is why `pom.xml` enables the `-Xcontext-parameters` Kotlin flag — and, like any extension, it must be **imported** (`import fi.oph.kitu.i18n.unaryPlus`) in each file that uses it. (There is deliberately no `t()`/`l()` helper and no Spring `MessageSource`; if you need the raw `String` — e.g. for an HTML attribute — call `someLocalizedString.toString()` (which resolves the ambient `CurrentLanguage`; pass an explicit `.get(lang)` only when you need a specific language).) `object`/static-`val` renderers (`html/Page.kt`, `html/Navigation.kt`) need no signature changes. The `html/Common.kt` article helpers are named **`errorMessage(LocalizedString)` / `warningMessage(LocalizedString)`** — not `error`/`warning` — precisely because a `FlowContent.error(String)` would let an accidental `error("literal")` silently resolve to Kotlin's stdlib `kotlin.error(Any): Nothing` (throws at runtime) instead of rendering an article. Keep those names distinct from `kotlin.error`. A **new** UI string is two lines: the key in `UiText.kt` and the Finnish in `lokalisointi/fi.json` (`UiTextTest` fails if you forget either). `LocalizedString(fi = "…")` remains correct for text that is _not_ catalog chrome — koodisto/organisaatio values and ad hoc strings — which never goes through `TolgeeMessages`. **Tolgee sourcing:** `tr(key)` returns `LocalizedString.withTolgeeKey(key)` — the object carries **only** the Tolgee key and resolves fi/sv/en **lazily** from `TolgeeMessages` on each `get()`/`toString()`/`interpolate()`/`contains()` (the key is a `private var` outside the data-class ctor, so `copy` ignores it; `equals`/`hashCode` are **hand-written to include it**, because every catalog string now has null fi/sv/en and would otherwise compare equal to every other one). Because resolution is lazy, a value stored in a `val` (e.g. a column-enum `uiHeaderValue`) **no longer freezes** — it tracks `LokalisointiScheduledTasks` refreshes, so the computed-getter / `when`-getter ceremony below still works but is no longer strictly required to avoid the freeze. When the store is empty or a key/locale is missing, `get()`'s fi fallback yields Finnish. `TolgeeMessages` (`i18n/TolgeeMessages.kt`) is a plain `object` with **two layers**: the _source texts_ read from the classpath (`lokalisointi/{fi,sv,en}.json`) during class initialization — deliberately **not** an `ApplicationRunner`, since runners execute only after the connector is already accepting requests — and the _live_ layer filled by `LokalisointiLoader`. The two are merged **per language** (`elava.fi ?: lahde.fi`, etc.) and the result is precomputed on write so `get()` stays one map lookup on the render hot path; a key-level replace would wipe the checked-in Swedish for keys whose live row carries only Finnish. `clear()` drops **only** the live layer, so `POST /kaannokset/tyhjenna-valimuisti` can never leave the UI without text. `setSourceTexts`/`reloadSourceTexts` exist for tests, which must restore **both** layers in `@AfterEach`. The store is filled at startup by `LokalisointiLoader` (an `ApplicationRunner`) which calls `LokalisointiClient` — it GETs flat per-locale JSON `/lokalisointi/tolgee/{namespace}/{locale}.json` from `https://{opintopolkuHostname}` and merges fi/sv/en into `Map<key, LocalizedString>`. `LokalisointiScheduledTasks` re-fetches on a db-scheduler interval (`kitu.lokalisointi.scheduling.*`). The cache can also be dropped by hand from the home page's Ylläpito card — `POST /kaannokset/tyhjenna-valimuisti` (`i18n/LokalisointiViewController`) clears `TolgeeMessages` and immediately reloads it, so a translator's change is visible without waiting for the interval. The controller is **unconditional** and takes the loader as an `ObjectProvider`, because the `LokalisointiLoader` bean does not exist when `kitu.lokalisointi.namespace` is empty (test/e2e/`local-opintopolku`) — there the route still clears the store and reports that lokalisointi is off. The **entire** lokalisointi machinery (client, RestClient config, loader, scheduled task) is gated by `@ConditionalOnNonEmptyProperty("kitu.lokalisointi.namespace")` — set in untuva/qa/prod only (`namespace=kielitutkintorekisteri`; the Tolgee **namespace** separates each app's translations in the shared lokalisointi service, cf. KOSKI's `koski`); in test/e2e/`local`/`local-opintopolku` the beans don't exist and the live layer stays empty, so everything renders from the checked-in `lokalisointi/*.json`. **`local` deliberately no longer fetches live**: untuva's proxy is ~160 keys behind and publishes no sv/en, so per-language merging would let its stale Finnish override fresher checked-in text. Translations are refreshed on demand with `python3 scripts/fetch_kaannokset.py` (defaults to the **QA** proxy, the only one carrying sv/en and the translator edits), reviewed as a git diff. The script never _adds_ keys — `fi.json` owns the key set — and editing an existing Finnish string there is pointless because Tolgee's `resolution: NEW` means it is overwritten on the next fetch; rename the key instead. Fetch failures never fail startup (the loader `runCatching`s and logs). No secret — the proxy serves published files. **Writing keys back to Tolgee (`i18n/tolgee/`)** — note this is a _different service_ from the read path: the lokalisointi proxy is read-only and has **no delete route**, so writes go **straight to Tolgee Cloud** (`https://app.tolgee.io`, `X-API-Key`). `tr` records each **key** (no text) into `UiTextRegistry`, and `TolgeeSyncService` takes the source text it pushes from `TolgeeMessages.sourceText(key)`, i.e. from `fi.json` — the source-text layer must never feed the registry, or QA would push Tolgee's own text back as source; `UiTextWarmup` (unconditional `ApplicationRunner`, `@Order(0)`) — both of those two files live in `i18n/`, **not** in `i18n/tolgee/`, which holds only the client/sync side — reflectively invokes every `UiText` member returning `LocalizedString` — properties, zero-arg functions, and functions whose params are all `Long` (called with `0L`s) — so the registry is complete regardless of what's been rendered. Then `TolgeeSyncRunner` (`@Order(100)`) diffs the registry against Tolgee's namespace and **creates missing keys and hard-deletes orphans**. Consequences worth knowing: (1) the warmup now **throws at boot** if any `LocalizedString` member can't be called (an uncallable member would look like a deleted key and get purged from Tolgee, losing translator work) — a `UiText` function taking a non-`Long` param is therefore a **startup failure**, in every profile including tests — **and it additionally throws if any `UiText` key is missing from `fi.json`**, since that key would otherwise render as a raw key string; because that check reads the global `UiTextRegistry`, a test that records a synthetic key into it breaks startup for every later test, so test catalogs must keep their fixtures out of the registry (see `UiTextWarmupTest`). `UiTextTest` pins the two key sets as **equal in both directions**, which is what keeps `UiText.kt` and `fi.json` from drifting; (2) the whole `tolgee` package is gated on `@ConditionalOnNonEmptyProperty("kitu.tolgee.apiKey")`, and the secret is injected **only into the QA task** (`props.name === "qa"` in `service-stack.ts`), so the secret's existence _is_ the environment restriction — there's no profile check; (3) deletes are capped by `max(kitu.tolgee.sync.minDeleteAllowance, maxDeleteRatio × Tolgee key count)` (default `max(5, 10%)`) — over the cap, creates still run, deletes are skipped, and the home page shows a warning driven by `TolgeeSyncStatus.last` (`tolgeeSyncWarning()`, a top-level `FlowContent` extension in `etusivu/HomePage.kt`); (4) `resolution: NEW` means an existing Tolgee source text is never overwritten — and since `get(FI)` prefers Tolgee's fi, a Finnish string edited in Tolgee keeps winning over the code no matter how you change the `tr(...)` literal, so **rename the key when a Finnish string's meaning changes**; (5) `kitu.tolgee.sync.dryRun=true` logs the diff without writing. `TolgeeClient` is an interface (impl `TolgeeClientImpl`) purely so tests can fake it with `object :` — this repo has no mocking library. Gotchas: (1) `Navigation.mainNavigation` **must stay a computed `val … get()`** (not a stored `val`): its `Links.*` URLs are built by HATEOAS `linkTo`, which reads the current request, so the list has to be rebuilt per render. (Its titles are lazy `LocalizedString`s and would no longer freeze.) The `?lang=`/cookie plumbing already works. - **Typed errors**: Arrow's `arrow.core.Either<E, V>` (left = error, right = value) is the project's convention for propagating domain errors out of services — prefer returning `Either` over throwing. Project-specific helpers live in `util/result/EitherExtensions.kt` (`getOrThrow` and `splitIntoValuesAndErrors`). `Either.fold(ifLeft, ifRight)` (note: ifLeft is the **first** named arg, opposite of the legacy `TypedResult.fold(onSuccess, onFailure)` order — always use named args).
- **Validation**: validators implement `Validation<T>` (`util/validation/Validation.kt`) — a three-phase pipeline of `validateBeforeEnrichment` → `enrich` → `validateAfterEnrichment` run by `validateAndEnrich`. The two `validate*` phases use the `ValidationRaise` typealias (= `Raise<NonEmptyList<ValidationError>>`) as their receiver and return `Unit` — the type system thus prevents transforming the value inside them. The sibling typealias `ValidationResult<T> = Either<NonEmptyList<ValidationError>, T>` covers the Either-shaped result. All transformation/derivation lives in `enrich`, whose receiver is the narrower `EnrichmentRaise` (= `Raise<ValidationError.EnrichmentError>`) — it may fail, but only with a single enrichment error, not an accumulated list. Checks that depend on the post-enrichment shape go in `validateAfterEnrichment` — see `YkiSuoritusValidation` where `enrich` optionally recomputes `arviointitila` via `laskeArviointitila` (only when `kitu.yki.convertLegacyArviointitila.enabled`, else passes the value through unchanged) and `validateAfterEnrichment` enforces "at least one osakoe" (`validateOsakokeitaOnAtLeastOne`, on the raw `osat`) plus that the arviointitila matches the arvosanat (`validateArviointitilaVastaaArvosanoja`). Compose sub-validators inside an `accumulate { … }` block (from `arrow.core.raise.accumulate`, `@OptIn(ExperimentalRaiseAccumulateApi::class)`), wrapping each call in `accumulating { … }` so all errors are collected in parallel rather than short-circuiting. Use `mapOrAccumulate` over collections, and `ensure` / `ensureNotNull` for predicates. Sub-validators that themselves accumulate take `RaiseAccumulate<ValidationError>` and nest further `accumulating { … }` blocks inside. Callers run a validator with `validator.validate(value)` (generic extension in `Validation.kt`; tiedonsiirto payloads go through `tiedontuontischema/TiedonsiirtoValidation`, which runs the common `HenkilosuoritusValidation` and then the VKT or YKI one), and the controller boundary uses `.orThrowBadRequest()` (also in `Validation.kt`) which throws `ValidationException(NonEmptyList<ValidationError>)` — the name deliberately differs from `util/result/EitherExtensions.kt`'s `getOrThrow`, which rethrows the Left and ends up a **500**, so importing the wrong one would silently swap the status code — caught by `GlobalControllerExceptionHandler` and turned into a 400.
- **Observability**: Spring's `spring-boot-starter-opentelemetry` + an explicit `opentelemetry-spring-boot-autoconfigure` dep (the latter supplies the `@WithSpan` aspect that Spring's starter drops). Traces exported OTLP to Jaeger locally (`docker-compose.yml` exposes UI on `:16686`). **Metrics are an allowlist:** the ADOT sidecar's `awsemf` exporter turns every meter × tag combination into a CloudWatch custom metric at $0.30/month, which until 10/2026 was the largest single AWS cost (~$220–265/month per env, ~1000 series). `application.properties` therefore sets `management.metrics.enable.all=false` and enables only `jvm.memory.used`, `hikaricp.connections.active/pending` and `dbscheduler_task_completions`; `otel.metrics.exporter=none` stops the OTel SDK from exporting a duplicate set, and the collector runs awsemf with `NoDimensionRollup` (the default re-exports every metric with no dimensions and with each single dimension). To add a meter, enable it there and check its tag cardinality first. Request and dependency latency/errors are free in the `ApplicationSignals` namespace, derived from the spans. Denying a meter does not touch tracing, so the `secured request` span below is unaffected. **Gotcha:** `@WithSpan` makes the bean a CGLIB proxy. A `@WithSpan` method **inherited from an abstract base class** reads that base class's constructor-injected fields as `null` at runtime (the proxy delegates the call in a way that skips the base-class field init), even though the same method+field on the concrete `@Service` works fine. So don't push injected dependencies (`Tracer`, repositories, `AuditLogger`) into an abstract base service — keep them on the concrete class and extract shared logic into top-level helper functions that take the deps as params (e.g. `restclient/OphServiceFetch.kt`'s `fetchOphService`, shared by the ONR, organisaatiopalvelu, ilmoittautumisjärjestelmä and ataru clients). **Toinen ansa — `Span.current()` ei ole HTTP-span:** kontrollerin rungossa ajossa oleva span on Spring Securityn `secured request` -observaatio (INTERNAL), **ei** SERVER-span. Spanipuu yhdelle pyynnölle on `kitu` (SERVER-segmentti: `uri`, `method`, `status.code`) → `secured request` (INTERNAL) → `@WithSpan`-metodit. Joten `Span.current().setAttribute(...)` kontrollerissa kirjoittaa attribuutin eri lokiriville kuin se, jolla reitti näkyy. Tällä on väliä, koska **CloudWatch Logsin metriikkasuodin tutkii yhden lokirivin kerrallaan**: `aws/spans`-suodin, joka vaatii sekä `$.attributes.uri`n että kontrollerin asettaman attribuutin, ei täsmää koskaan — ja vikaantuu hiljaa, koska `treatMissingData: NOT_BREACHING` tekee emittoimattomasta metriikasta erottamattoman siitä ettei mitään tapahtunut (näin `PostYkiSuoritus` oli nollissa 4.6.–16.9.2026). Suodata siis kontrollerin omaan attribuuttiin, älä yritä yhdistää kahden spanin kenttiä, ja **validoi suodinlauseke oikeaa dataa vasten** `aws logs test-metric-filter`illa ennen deployta. Muista myös ettei suodinlauseke voi viitata pisteellisiin JSON-avaimiin, joten attribuuttien nimien on oltava pisteettömiä.
- **Lokirivit pidetään alle 16 kt:n (OPHKOTO-91)**: Fargaten `awslogs` pilkkoo yli 16 kt:n stdout-rivin useaksi CloudWatch-tapahtumaksi, jotka eivät ole JSONia, jolloin `LogErrors`-hälytyksen `$.log.level`-suodin ohittaa juuri ne virheet, joilla on pisin pinojälki (KOSKI korjasi saman: `f84b4289fe`, `194a511aa5`). `observability/LogLineSizeLimits` (`logging.structured.json.customizer`) katkaisee merkkijonoarvot JSON-koodattujen UTF-8-tavujen mukaan (`message` 3072, `error.stack_trace` 8192, `error.message` 1024, muut 512; aina merkkirajalla — pinojälki saa suurimman osuuden, koska Devin pisimmät oikeat pinojäljet ovat 8–9 kt), ja pinojälki tulostetaan juurisyy edellä (`stacktrace.root=first`, `max-throwable-depth=50`), jotta katkaisu osuu uloimpiin kääreisiin. Sama customizer koskee audit-encoderia, joten `AuditLogger` **heittää ennen kirjausta**, jos merkintä ei mahdu budjettiin (KOSKIn käytäntö: kirjaamaton toimenpide ei saa onnistua) — katkaistu `message` rikkoisi KOSKI-audit-Lambdan `JSON.parse`n. `PutLogEvents`-virhe ei sen sijaan kaada toimenpidettä (logback nielee appenderin poikkeukset), mutta lokittuu ERRORina. **Huom:** `src/test/resources/application.properties` varjostaa pääkonfiguraation, joten `logging.*`-asetukset on lisättävä molempiin.
- **RestClient message converters**: configure via the SB4 DSL `configureMessageConverters { cs -> cs.registerDefaults()... }`, not the deprecated `messageConverters(...)`. Use `withJsonConverter(JacksonJsonHttpMessageConverter(mapper))` to swap Jackson, and `configureMessageConvertersList { list -> list.add(0, x) }` when ordering matters. Any `RestClient` that reads a JSON body into `String` (including `retrieveEntitySafely(String::class.java)`) must call `.withLenientStringConverter()` from `restclient/RestClientExtensions.kt` — Spring 7's default `StringHttpMessageConverter` only advertises `text/*`, so without the helper the call fails inside Jackson.
- **Spring HATEOAS 3 `linkTo` DSL**: tracks the controller invocation via the lambda's **return value** (not a thread-local), so the lambda signature must be `(C) -> Any`. A `C.() -> Unit` receiver lambda collapses to `Unit` and bypasses the proxy's `LastInvocationAware` tracking — see `html/Navigation.kt`.
- **Testcontainers 2.x**: artifacts are prefixed (`testcontainers-postgresql`, `testcontainers-junit-jupiter`) and `PostgreSQLContainer` moved to `org.testcontainers.postgresql.PostgreSQLContainer` (no generic parameter). On macOS set `DOCKER_HOST="unix://${HOME}/.docker/run/docker.sock"` if the socket isn't auto-detected.

- **Lambda runtimes are never pinned, and orphan stacks are the hazard**: the two Lambdas the repo owns (`koski-audit-logs-integration-stack.ts` and YkiSuoritusNotifications in `log-groups-stack.ts`) uses `Runtime.NODEJS_LATEST`, and CDK's own custom-resource Lambdas use `determineLatestNodeRuntimeName()` — both _variable_ values that move when `aws-cdk-lib` is bumped. Renovate automerges those bumps and every `main` push redeploys, so runtimes stay current by themselves; **do not pin a runtime to "fix" a deprecation warning**. What actually goes stale is a CloudFormation stack that was renamed or deleted in code but never deleted in AWS: CDK stops managing it and its resources freeze forever (this is where every `nodejs20.x` Lambda in this project came from — `Prod-AlarmsStack`, `CertificateStack`, and the writer left behind in the legacy `DnsStack`). **When you remove or rename a stack, delete the old CFN stack in every account in the same change.** `infra/scripts/audit-deployed-stacks.sh` (run weekly by `.github/workflows/aws-audit.yml`) diffs deployed stacks and Lambda runtimes against the synthesized app and reports the drift; `alarms-stack.ts` additionally forwards `aws.health` `scheduledChange` events to Slack so EOL notices are seen. Two related traps: `PhysicalName.GENERATE_IF_NEEDED` on the alarms SNS topics is what keeps the us-east-1 ↔ eu-west-1 sharing free of `crossRegionReferences` (removing it re-materializes a pair of custom-resource Lambdas per stack), and the per-env `DnsStack` that owns the Route53 zone is _deliberately_ outside the CDK app — the in-app `<Env>/Dns` only does `HostedZone.fromLookup` and synthesizes to an empty stack.
- **Application log groups are CMK-encrypted (OPHKOTO-94)**: `KituService`, `KituServiceAudit` and `KituServiceDataProtectionAudit` use `LogsKey` (`alias/kitu/logs`) in `log-groups-stack.ts`. Writes encrypt as the CloudWatch Logs service, but reads (`FilterLogEvents`, live tail) make a KMS `Decrypt` call **as the calling role** — so the key policy's `kms:ViaService` + `kms:CallerAccount` statement is what lets the deploy job's live tail and roles without `kms:Decrypt` in IAM read the logs — **don't remove it**. A new group encrypted with the key must also go into `LOG_GROUP_NAMES` (the service principal's encryption-context list), or the association fails. Events from before the change stay under the default encryption until the 731-day retention expires them; see `infra/README.md` "Log group encryption".
- **GitHub Actions OIDC trust is exact, and a mistake locks CI out**: `kitu-github-actions-role` trusts only `repo:Opetushallitus/kielitutkintorekisteri:environment:<Util|Dev|Test|Prod>` (+ `ref:refs/heads/main` in Util for the ECR push), and `kitu-github-actions-diff-role` only `…:pull_request`, with CloudFormation template reads and nothing else (deliberately **not** the CDK lookup role, whose `ReadOnlyAccess` would let any PR read S3). The environment in the `sub` is the **workflow's spelling** (`Dev`), compared case-sensitively, and any job declaring `environment:` gets it regardless of trigger — the environments' "main only" branch policy is what keeps PRs and branch dispatches out. The trust is deployed by CI with the role itself, so a wrong subject fails only on the next run; recovery is a local `cdk deploy --exclusively '<Env>/GithubActions'`. Check real subjects from CloudTrail first (snippet in `infra/README.md` "GitHub Actions roles").

### Deployments

`main` pushes auto-deploy through `.github/workflows/build.yml`. Full chain: `verified_in_queue` → `server_tests ∥ frontend_tests ∥ lint ∥ infra_lockfile ∥ build_image` (pushed to the `Util` account ECR) `∥ deploy_util ∥ submit_dependencies` → `deploy_dev` (waits for both the image and the tests) → `deploy_test` → `deploy_prod` → `build_docs` (GitHub Pages). **Tests are skipped on main when the merge queue already passed the same SHA**: the queue fast-forwards main to exactly the commit it tested, so `verified_in_queue` reads the commit's check runs and outputs `verified=true` when all four test/lint checks are `success`/`skipped` there; a direct push to main runs everything. On PRs and in the queue, `server_tests`/`frontend_tests` are additionally skipped by `list_changes`' `server`/`e2e` path filters (infra-only, docs-only, scripts-only changes). Since any of those may be skipped, every deploy job's `if:` checks `!cancelled()` plus the direct dependency's `result == 'success'` explicitly — a bare implicit `success()` would let a skipped upstream job silently skip the whole deploy chain. PR runs cancel superseded ones via workflow-level `concurrency`; on main and in the queue the group is per-run on purpose (a shared group would replace a pending main run and skip its deploy). The four deploy jobs all call `_deploy-env.yml`; **`deploy_util` is a real job that `deploy_dev` depends on** — don't omit it. The `lint` job runs `check-formatting.sh` _and_ `check-workflows.sh`. On PRs, `determine_action` flips the action to `diff`; when the PR touches `infra/` (`list_changes`' `infra` filter), Util, Dev, Test and Prod each post a `cdk-notifier` comment instead of deploying (not in the merge queue). `_deploy-env.yml` has two jobs: `deploy` (GitHub environment + `kitu-github-actions-role`) and `diff` (**no** environment, so the OIDC subject is `…:pull_request`, + `kitu-github-actions-diff-role` and `cdk diff --method=template`). Don't give the diff job an environment: that would hand PR code the deploy role, and the environments' "main only" branch policy would reject the job anyway. Concurrency is **per job**: `deploy-<Env>` (every ref, never cancelled, because two deploys would update the same stacks; GitHub keeps one pending job per group, so a third arrival replaces the pending one) and `diff-<ref>-<Env>` (cancel-in-progress). Never put a diff in the deploy group, where its `cancel-in-progress` would kill a running deploy. `deploy_test`/`deploy_prod` therefore just follow `deploy_dev`'s result, and `build_docs` is the job that must check `action == 'deploy'` itself, since `deploy_prod` also succeeds as a PR diff. **A `needs.<job>` reference to a job missing from that job's `needs:` list evaluates to empty, not an error** — that is how `deploy_dev`'s infra branch was dead from 11/2024 (`953e97d6`) to 10/2026 and no PR got an env diff; `actionlint` flags it. Four AWS accounts (`infra/lib/accounts.ts`, all listed in the README): dev `682033502734`, test `961341546901`, prod `515966535475`, and the shared utility account `961341524988`.

**Renovate ja `infra/package-lock.json`:** Renovate ei osaa päivittää lockia `aws-cdk-lib`ille (ainoa `bundleDependencies`-riippuvuus), vaan jättää `renovate/artifacts`-statuksen punaiseksi ja avaa PR:n jossa on muuttunut **vain `infra/package.json`**. Kerran desynkatussa puussa myös `aws-cdk`-nostot epäonnistuvat samalla tavalla, ja `npm ci` kaatuu vasta mainissa. `^`-alueelliset riippuvuudet (aws-sdk-js-v3 yms.) eivät kärsi tästä, koska Renovate päivittää niiden lockin omalla `updateLockedDependency`-koodillaan ajamatta npm:ää lainkaan. Kaksi toisiaan täydentävää suojaa: `skipInstalls: false` (täysi `npm install` `--package-lock-only`:n sijaan, jolloin niputetut riippuvuudet resolvoituvat) ja `Infra lockfile in sync` -työ **pakollisena** tarkistuksena repon rulesetissä — jälkimmäinen on se joka tosiasiassa pysäyttää desynkan, sillä se kaataa `npm ci`:n jo PR:ssä. **Älä lisää `renovate/artifacts`ia pakolliseksi tarkistukseksi** — ihmisten PR:t eivät koskaan saa sitä ja jäisivät ikuisesti jumiin. Huom: `platformAutomerge` oli aiemmin `false` kolmantena suojana (Renovate mergeää vasta kun _jokainen_ tarkistus on vihreä, GitHubin oma automerge odottaa vain pakollisia), mutta merge queuen myötä se **on pakko olla `true`** — ks. alla.

**Merge queue:** mainiin ei mergetä suoraan vaan rulesetin merge queuen läpi (`rebase`, 1–5 entryä, ALLGREEN). Syy: `rebaseWhen`in oletus `auto` = `behind-base-branch` kun automerge on päällä, joten jokainen mainiin tuleva commit nollasi kaikkien Renovate-haarojen tarkistukset — vihreä ikkuna ~14 min, Renovaten ajoväli ~28 min, eli PR:t mergeytyivät käytännössä vain öisin. Jono testaa entryn **mainin kärkeä vasten** ennen mergeä, joten `rebaseWhen: "conflicted"` on nyt turvallinen (aiemmin se hylättiin juuri siksi, ettei vanhentunutta haaraa testattaisi yhdessä uusien versioiden kanssa — merge queue poistaa tuon riskin). Kaksi asiaa joita **ei saa rikkoa**: (1) `build.yml`illa on oltava `merge_group:`-triggeri, muuten pakolliset tarkistukset eivät raportoi jonossa lainkaan ja entry **aikakatkeaa 60 min päästä** — eli mikään ei mergeydy; (2) `platformAutomerge: true`, koska jonon takana Renovaten oma REST-merge hylätään ("Changes must be made through the merge queue") — GitHubin natiivi automerge on se joka asettaa PR:n jonoon. Jonoajossa `github.ref_name` on `gh-readonly-queue/main/...`, ei `main`, joten deployt ja ECR-push eivät laukea; `list_changes` ajaa `paths-filter`in jonossakin (se vertaa `merge_group.base_sha..head_sha`, eli kaikkea mitä entry ja sitä edeltävät tuovat mainin päälle), mutta `image`, `infra` ja `mise` pakotetaan jonossa `true`ksi, jolloin `build_image` oikeasti ajetaan jonossa mutta ilman pushia, ja `deploy_util` on erikseen estetty `github.event_name != 'merge_group'` -ehdolla.

## Conventions

- **Language**: user-facing text, commit messages, and PR titles are in Finnish. Kotlin/TS identifiers are Finnish/English mix following existing usage in the touched package — follow the surrounding file.
- **CSV exports**: never rename or remove a column without asking, and always append new columns at the end (see "Display tables & CSV export").
- **Formatting**: ktlint (K2 mode, format-on-save in IDEA) for Kotlin; prettier for TS/JSON/YAML/MD; shellcheck for `scripts/*.sh` and `infra/scripts/*.sh`. `.git-blame-ignore-revs` tracks formatting-only commits — add new bulk-reformat commits there.
- **Always run `./scripts/format.sh` before reporting a task done** whenever TS/JSON/YAML/MD (or Kotlin) files have been touched. The script runs `prettier --write .` and `ktlint --format`, matching what `check-formatting.sh` enforces in CI.
- **Workflows**: after editing `.github/workflows/`, run `./scripts/check-workflows.sh` (the CI `lint` job's second step). It bans `pull_request_target` and runs `actionlint`, which also shellchecks every `run:` block and type-checks expressions. That includes `needs.<job>` references: one pointing at a job missing from `needs:` evaluates silently empty in GitHub, not as an error. A freshly `mise install`ed tool only lands on a non-interactive shell's PATH via `mise exec --`. actionlint checks `runs-on` against its own built-in list of GitHub-hosted labels, so a newer runner (e.g. Renovate bumping to `ubuntu-26.04`) fails the **required** lint check with `label "…" is unknown`. Declare such labels in `.github/actionlint.yaml` (`self-hosted-runner.labels`) until the pinned actionlint knows them.
- **Banned dependencies**: `pom.xml` enforces exclusions for vulnerable `bouncycastle` and `xmlunit-core` versions; don't let transitive updates reintroduce them.
- **Keep `infra/README.md` accurate**: any change under `infra/lib/` or `infra/bin/` that affects which stacks exist, what they create, IAM identities, cross-account wiring, manual prerequisites (DNS zones, secrets, KOSKI-side resources), or the Slack/alarms/investigation flow must update `infra/README.md` in the same commit.
